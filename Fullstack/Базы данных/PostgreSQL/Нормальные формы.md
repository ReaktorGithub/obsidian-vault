**Нормализация** - это процесс организации таблиц базы данных, который уменьшает дублирование данных и предотвращает аномалии при добавлении, изменении и удалении записей.

**Нормальные формы** - это набор правил, которым должна соответствовать структура таблиц, чтобы считаться нормализованной на определённом уровне.

Нормализация - это не особая команда PostgreSQL, а принцип проектирования реляционных баз данных.

### Зачем нужна нормализация?

Предположим, есть таблица заказов:

|order_id|customer_name|customer_phone|product|
|---|---|---|---|
|1|Иван|111-11-11|Ноутбук|
|2|Иван|111-11-11|Мышь|
|3|Анна|222-22-22|Клавиатура|

Здесь имя и телефон Ивана повторяются в каждой его покупке.

Это создаёт три проблемы:

- **Избыточность:** данные клиента дублируются.
- **Аномалия обновления:** при смене телефона нужно изменить несколько строк.
- **Аномалия удаления:** при удалении последнего заказа клиента можно потерять информацию о нём.

Решение - вынести клиентов в отдельную таблицу и связать её с заказами через внешний ключ (`FOREIGN KEY`).

**Таблица customers:**

|customer_id|name|phone|
|---|---|---|
|1|Иван|111-11-11|
|2|Анна|222-22-22|

**Таблица orders:**

|order_id|customer_id|product|
|---|---|---|
|1|1|Ноутбук|
|2|1|Мышь|
|3|2|Клавиатура|

Теперь информация о каждом клиенте хранится в одном месте.

## Основные нормальные формы

### Первая нормальная форма (1NF)

**Правила:**

- Каждая ячейка содержит одно значение, а не список значений.
- Нет повторяющихся групп столбцов.
- Каждая строка должна однозначно идентифицироваться, обычно с помощью первичного ключа.

Пример нарушения:

|user_id|name|phones|
|---|---|---|
|1|Иван|111-11-11, 222-22-22|

Правильнее хранить телефоны в отдельной таблице:

|user_id|phone|
|---|---|
|1|111-11-11|
|1|222-22-22|

Так каждый телефон представлен отдельной записью.

Важно: PostgreSQL позволяет хранить массивы и JSON, но сам факт использования этих типов не означает автоматически нарушение 1NF. Вопрос в том, как организованы данные и используются ли они как неделимые значения в рамках выбранной модели.

### Вторая нормальная форма (2NF)

**Правило:** таблица находится в 1NF, и каждый неключевой атрибут зависит от всего потенциального ключа, а не только от его части.

Это особенно важно для таблиц с составным ключом.

Например, таблица оценок:

|student_id|course_id|student_name|grade|
|---|---|---|---|
|1|101|Иван|5|
|1|102|Иван|4|
|2|101|Анна|3|

Предположим, первичный ключ - `(student_id, course_id)`.

- `grade` зависит от студента и курса одновременно.
- `student_name` зависит только от `student_id`.

Следовательно, `student_name` зависит лишь от части составного ключа, что нарушает 2NF.

Решение - разделить данные на две таблицы:

**students**

|student_id|student_name|
|---|---|
|1|Иван|
|2|Анна|

**grades**

|student_id|course_id|grade|
|---|---|---|
|1|101|5|
|1|102|4|
|2|101|3|

### Третья нормальная форма (3NF)

**Правило:** таблица находится во 2NF, и неключевые атрибуты не должны транзитивно зависеть от ключа через другие неключевые атрибуты.

Проще говоря, неключевые столбцы должны зависеть от ключа, а не друг от друга.

Пример:

|employee_id|employee_name|department_id|department_name|
|---|---|---|---|
|1|Иван|10|Разработка|
|2|Анна|10|Разработка|
|3|Пётр|20|Продажи|

Здесь:

- `employee_id` определяет сотрудника и его отдел.
- `department_id` определяет `department_name`.
- Следовательно, название отдела зависит от `employee_id` через `department_id`.

Это транзитивная зависимость.

Решение - разделить таблицу.

**employees**

|employee_id|employee_name|department_id|
|---|---|---|
|1|Иван|10|
|2|Анна|10|
|3|Пётр|20|

**departments**

|department_id|department_name|
|---|---|
|10|Разработка|
|20|Продажи|

Теперь название каждого отдела хранится в одном месте.

### Нормальная форма Бойса — Кодда (BCNF)

**Правило:** для каждой нетривиальной функциональной зависимости `X → Y` атрибуты `X` должны образовывать суперключ.

BCNF строже третьей нормальной формы и устраняет некоторые аномалии, которые могут оставаться даже при соблюдении 3NF.

На практике к BCNF обращаются при проектировании сложных схем, когда между атрибутами существуют нетривиальные зависимости.

### Четвёртая нормальная форма (4NF)

**Правило:** таблица находится в BCNF и не содержит нетривиальных многозначных зависимостей, источник которых не является суперключом.

Например, у преподавателя независимо друг от друга могут быть несколько предметов и несколько языков преподавания.

Если хранить их в одной таблице, может возникнуть избыточность из-за комбинаций каждого предмета с каждым языком.

Решение - хранить предметы и языки в отдельных таблицах связей.

### Пятая нормальная форма (5NF)

**Правило:** таблица не должна содержать нетривиальных зависимостей соединения, кроме тех, которые следуют из её потенциальных ключей.

Она нужна для более сложных случаев, когда данные можно разделить на несколько таблиц без потери информации, но при этом простые зависимости между отдельными столбцами не объясняют такую возможность полностью.

В обычных приложениях 5NF требуется значительно реже, чем 1NF, 2NF и 3NF.

## Как это связано с PostgreSQL?

PostgreSQL не нормализует таблицы автоматически. Нормализацию выполняет разработчик при проектировании схемы базы данных.

Для этого используются обычные инструменты SQL:

- `CREATE TABLE` - создание таблиц.
- `PRIMARY KEY` - определение первичного ключа.
- `FOREIGN KEY` - связь между таблицами.
- `UNIQUE` - обеспечение уникальности значений.
- `JOIN` - объединение данных из нескольких таблиц при запросе.

Например:

```
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    phone VARCHAR(20)
);

CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INTEGER NOT NULL
        REFERENCES customers(customer_id),
    total NUMERIC(10, 2) NOT NULL
);
```

Здесь информация о клиентах хранится отдельно от заказов. Связь между таблицами устанавливается через `FOREIGN KEY`.

Получить заказы вместе с именами клиентов можно так:

```
SELECT
    o.order_id,
    c.name,
    o.total
FROM orders o
JOIN customers c
    ON o.customer_id = c.customer_id;
```

## Кратко для собеседования

|Форма|Основное требование|
|---|---|
|**1NF**|Каждая ячейка содержит одно значение, отсутствуют повторяющиеся группы|
|**2NF**|1NF + отсутствие частичных зависимостей неключевых атрибутов от составного потенциального ключа|
|**3NF**|2NF + отсутствие недопустимых транзитивных зависимостей неключевых атрибутов от ключа|
|**BCNF**|Для каждой нетривиальной функциональной зависимости её детерминант является суперключом|
|**4NF**|Отсутствие недопустимых многозначных зависимостей|
|**5NF**|Отсутствие недопустимых зависимостей соединения|

**Главное, что нужно запомнить:** нормализация уменьшает дублирование и предотвращает аномалии изменения данных. В большинстве типичных приложений достаточно правильно спроектировать таблицы до третьей нормальной формы. При необходимости производительности иногда применяют денормализацию - намеренное дублирование данных, чтобы упростить или ускорить чтение.
