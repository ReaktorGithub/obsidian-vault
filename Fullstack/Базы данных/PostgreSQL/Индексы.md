**Индекс** - это структура данных, которая ускоряет поиск строк в таблице, но требует дополнительного места и замедляет некоторые операции изменения данных.

Без индекса PostgreSQL может выполнять `Sequential Scan` - последовательно проверять строки таблицы. При наличии подходящего индекса он может использовать его для поиска нужных строк.

## Создание индексов

### CREATE INDEX

```
-- Обычный индекс
CREATE INDEX idx_users_name
ON users (name);

-- Уникальный индекс
CREATE UNIQUE INDEX idx_users_email
ON users (email);

-- Удаление индекса
DROP INDEX idx_users_name;
```

`UNIQUE` запрещает появление дубликатов индексируемых значений. При этом обычный индекс сам по себе не гарантирует уникальность.

По умолчанию PostgreSQL создаёт индекс типа **B-tree**.

### Когда нужны индексы?

Индексы особенно полезны для столбцов, которые часто используются в:

- `WHERE` - фильтрация;
- `JOIN` - соединение таблиц;
- `ORDER BY` - сортировка;
- `GROUP BY` - группировка, в некоторых случаях;
- проверках ограничений `UNIQUE`, а также для поиска связанных строк при работе с внешними ключами.

Например:

```
CREATE INDEX idx_orders_user_id
ON orders (user_id);

SELECT *
FROM orders
WHERE user_id = 10;
```

Индекс может ускорить поиск заказов пользователя с `id = 10`.

**Важно:** индекс не гарантирует ускорение каждого запроса. Если таблица маленькая или запрос возвращает большую часть строк, PostgreSQL может предпочесть последовательное сканирование.

## Типы индексов

В PostgreSQL есть несколько типов индексов, предназначенных для разных задач.

|Тип|Особенности|Когда использовать|
|---|---|---|
|`B-tree`|Сбалансированное дерево; поддерживает равенство, диапазоны и сортировку|Большинство стандартных запросов|
|`Hash`|Индекс для сравнения на равенство|Когда нужны только проверки `=`|
|`GIN`|Индексирует компоненты составных значений|Массивы, JSONB, полнотекстовый поиск|
|`GiST`|Универсальная индексная структура для специализированных операторов|Геометрические данные, диапазоны, пространственный поиск|
|`SP-GiST`|Поддерживает разбиение пространства поиска на непересекающиеся области|Некоторые деревья, пространственные структуры|
|`BRIN`|Хранит сводную информацию о диапазонах физических блоков таблицы|Очень большие таблицы, где значения связаны с физическим порядком строк|

### B-tree

Самый распространённый тип индекса.

```
CREATE INDEX idx_products_price
ON products (price);
```

Подходит для запросов:

```
SELECT *
FROM products
WHERE price = 1000;

SELECT *
FROM products
WHERE price > 500;

SELECT *
FROM products
ORDER BY price;
```

B-tree поддерживает сравнения `=`, `<`, `<=`, `>`, `>=`, а также некоторые другие операции, включая поиск по диапазону.

Сложность поиска: O(log n)

### Hash

Используется для сравнений на равенство.

```
CREATE INDEX idx_users_id_hash
ON users USING HASH (id);
```

Подходит для условий вида:

```
SELECT *
FROM users
WHERE id = 10;
```

Для большинства стандартных случаев обычно достаточно B-tree.

Сложность поиска: O(1)

### GIN

GIN (Generalized Inverted Index) удобен для поиска по составным значениям, например по элементам массива или ключам JSONB.

```
CREATE INDEX idx_articles_tags
ON articles USING GIN (tags);
```

Если `tags` - массив, можно искать статьи, содержащие определённый тег:

```
SELECT *
FROM articles
WHERE tags @> ARRAY['postgresql'];
```

GIN также широко применяется для JSONB и полнотекстового поиска.

### GiST

GiST (Generalized Search Tree) позволяет создавать индексы для разных типов данных и специализированных операторов.

Применяется, например, для пространственных данных и поиска пересечений диапазонов. Конкретные возможности зависят от типа данных и операторного класса.

### BRIN

BRIN (Block Range INdex) хранит краткую информацию о значениях в диапазонах физических блоков таблицы.

```
CREATE INDEX idx_logs_created_at
ON logs USING BRIN (created_at);
```

Полезен для очень больших таблиц журналов, если `created_at` примерно соответствует порядку физического размещения строк.

BRIN занимает мало места, но обычно менее точен при поиске отдельных строк, чем B-tree.

## Индексы по нескольким столбцам

Можно создать один индекс сразу по нескольким столбцам.

```
CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
```

Такой индекс особенно полезен для запросов:

```
SELECT *
FROM orders
WHERE user_id = 10;

SELECT *
FROM orders
WHERE user_id = 10
  AND status = 'paid';
```

Но он не так хорошо подходит для запроса только по `status`:

```
SELECT *
FROM orders
WHERE status = 'paid';
```

**Почему?** В B-tree составном индексе важен порядок столбцов. Наиболее эффективно он работает, когда условия поиска включают ведущие столбцы индекса.

Для индекса `(user_id, status)` ведущий столбец - `user_id`.

Поэтому порядок столбцов нужно выбирать исходя из запросов приложения, а не просто по количеству столбцов.

## Уникальные индексы

Уникальный индекс гарантирует, что индексируемые значения не будут дублироваться.

```
CREATE UNIQUE INDEX idx_users_email
ON users (email);
```

Теперь нельзя вставить две строки с одинаковым непустым `email`.

**Нюанс:** по умолчанию PostgreSQL допускает несколько `NULL` в уникальном индексе, поскольку они считаются различными значениями для проверки уникальности. Для запрета нескольких `NULL` можно использовать `NULLS NOT DISTINCT` в поддерживающих эту возможность версиях PostgreSQL.

Ограничения `PRIMARY KEY` и `UNIQUE` автоматически создают необходимые уникальные индексы.

## Частичные индексы (Partial Index)

Частичный индекс содержит только строки, соответствующие определённому условию.

```
CREATE INDEX idx_orders_pending
ON orders (created_at)
WHERE status = 'pending';
```

Он может ускорить запросы:

```
SELECT *
FROM orders
WHERE status = 'pending'
ORDER BY created_at;
```

Преимущество: индекс меньше и дешевле в обслуживании, чем индекс по всем строкам таблицы.

Важно, чтобы PostgreSQL мог установить соответствие между условием запроса и предикатом индекса.

## Индексы по выражениям

Можно индексировать не только значения столбцов, но и результаты выражений.

```
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));
```

Такой индекс может ускорить запрос:

```
SELECT *
FROM users
WHERE LOWER(email) = LOWER('USER@EXAMPLE.COM');
```

Без подходящего индекса PostgreSQL может вычислять `LOWER(email)` для большого количества строк.

Индексы по выражениям полезны, когда запросы регулярно используют одни и те же вычисления.

## Покрывающие индексы и INCLUDE

`INCLUDE` позволяет добавить в индекс дополнительные столбцы, которые не участвуют в поиске, но могут понадобиться при чтении результата.

```
CREATE INDEX idx_users_email
ON users (email)
INCLUDE (name);
```

Запрос:

```
SELECT name
FROM users
WHERE email = 'user@example.com';
```

В некоторых случаях PostgreSQL сможет выполнить `Index Only Scan`, получив необходимые значения из индекса без чтения данных таблицы.

Однако это зависит в том числе от видимости строк и состояния visibility map: наличие `INCLUDE` не гарантирует, что обращения к таблице не понадобятся.

## Как проверить использование индекса?

Для анализа плана выполнения используется `EXPLAIN`.

```
EXPLAIN
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Для выполнения запроса с измерением фактического времени:

```
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Обрати внимание на основные типы сканирования:

|Операция|Значение|
|---|---|
|`Seq Scan`|Последовательное чтение таблицы|
|`Index Scan`|Поиск через индекс с обращением к таблице за данными|
|`Index Only Scan`|Получение необходимых данных преимущественно из индекса|
|`Bitmap Index Scan`|Поиск подходящих записей через индекс с формированием битовой карты|
|`Bitmap Heap Scan`|Чтение строк таблицы по битовой карте|

`Seq Scan` не обязательно означает плохую производительность. Для маленьких таблиц или запросов, возвращающих большую часть строк, он может быть эффективнее индекса.

## Недостатки индексов

1. **Дополнительное место.** Индексы хранят отдельные структуры данных.
2. **Замедление записи.** При `INSERT`, `UPDATE` и `DELETE` соответствующие индексы приходится обслуживать.
3. **Обслуживание.** Индексы могут разрастаться и требовать анализа или перестроения в определённых ситуациях.
4. **Не каждый индекс используется.** Неподходящий или избыточный индекс может лишь занимать место и замедлять запись.

Поэтому не стоит создавать индексы на всех столбцах автоматически. Их выбирают на основе реальных запросов и проверяют через `EXPLAIN ANALYZE`.

## Кратко для собеседования

- **Индекс** - структура данных для ускорения поиска, которая требует дополнительного места и увеличивает стоимость операций записи.
- **B-tree** - тип индекса по умолчанию; подходит для равенства, диапазонов и сортировки.
- **GIN** - поиск по элементам массивов, JSONB и полнотекстовым данным.
- **GiST** - специализированный поиск, например пространственных данных и диапазонов.
- **BRIN** - компактный индекс для больших таблиц, где значения коррелируют с физическим порядком строк.
- **Составной индекс** - индекс по нескольким столбцам, для которого важен их порядок.
- **Частичный индекс** - индекс только для строк, удовлетворяющих условию.
- **Индекс по выражению** - индексирует результат выражения, например `LOWER(email)`.
- **`EXPLAIN ANALYZE`** - позволяет изучить план выполнения и фактические показатели запроса.
- **`Index Only Scan`** - позволяет читать необходимые данные из индекса, когда это возможно без обращения к таблице.

## VACUUM

**`VACUUM`** - команда, которая очищает таблицы от пространства, занимаемого устаревшими версиями строк, которые стали ненужными после `UPDATE` и `DELETE`.

PostgreSQL использует MVCC: при обновлении строки обычно создаётся новая версия, а старая не удаляется сразу. Поэтому со временем в таблицах накапливаются устаревшие версии строк.

### Основные команды

**`VACUUM`** - освобождает место, занимаемое мёртвыми версиями строк, для повторного использования внутри таблицы.

```
VACUUM users;
```

**`VACUUM FULL`** - переписывает таблицу, компактно размещая данные и возвращая освободившееся пространство операционной системе.

```
VACUUM FULL users;
```

Отличия:

|Характеристика|`VACUUM`|`VACUUM FULL`|
|---|---|---|
|Удаляет мёртвые версии строк|Да|Да|
|Компактно переписывает таблицу|Нет|Да|
|Возвращает место ОС|Обычно нет|Да|
|Блокирует обычные операции чтения и записи на время работы|Нет|Да|
|Требует дополнительного дискового пространства|Обычно немного|Может потребоваться значительное|

Обычный `VACUUM` не обязательно уменьшает размер файла таблицы, но позволяет повторно использовать освободившееся пространство для новых данных.

### VACUUM ANALYZE

```
VACUUM ANALYZE users;
```

Выполняет две операции:

- `VACUUM` - очищает устаревшие версии строк.
- `ANALYZE` - собирает статистику о данных, которую планировщик запросов использует для выбора плана выполнения.

**Важно:** `VACUUM` не заменяет `ANALYZE`. Обычный `VACUUM` может обновлять статистику видимости страниц, но для сбора статистики распределения данных предназначен `ANALYZE`.

### Autovacuum

**Autovacuum** - автоматический механизм PostgreSQL, который запускает очистку таблиц и обновление статистики при необходимости.

Он помогает:

- предотвращать чрезмерное накопление мёртвых версий строк;
- поддерживать актуальность статистики планировщика;
- предотвращать переполнение счётчика транзакций (`transaction ID wraparound`).

Обычно autovacuum не нужно отключать: без него таблицы могут разрастаться, а производительность запросов - ухудшаться.

## FSM (Free Space Map)

**FSM (Free Space Map)** - карта свободного пространства, которая хранит информацию о количестве свободного места на страницах таблицы или индекса.

PostgreSQL использует FSM, чтобы быстрее находить страницы, в которых достаточно места для размещения новых данных.

Например, после обновления или удаления строк на странице таблицы может освободиться место. FSM помогает PostgreSQL определить, где это место можно использовать повторно.

### Как связаны VACUUM и FSM?

1. `UPDATE` и `DELETE` приводят к появлению устаревших версий строк.
2. `VACUUM` определяет, какие версии строк больше не нужны, и очищает их.
3. Освободившееся пространство становится доступным для повторного использования.
4. Информация о свободном месте обновляется в FSM.
5. При последующих вставках PostgreSQL может использовать страницы с доступным пространством.

FSM не хранит сами данные и не очищает таблицы. Она только помогает находить свободное место.

### FSM и Visibility Map

Не путай эти два механизма:

|Механизм|Назначение|
|---|---|
|FSM (Free Space Map)|Информация о свободном месте на страницах|
|Visibility Map|Информация о том, содержат ли страницы только версии строк, видимые всем транзакциям|

Visibility Map позволяет PostgreSQL эффективнее выполнять `Index Only Scan`, поскольку для некоторых страниц становится возможным не обращаться к самой таблице для проверки видимости строк.

## Кратко для собеседования

- `VACUUM` - очищает таблицу от устаревших версий строк, позволяя повторно использовать освободившееся пространство.
- `VACUUM FULL` - переписывает таблицу, возвращая свободное пространство операционной системе, но требует сильной блокировки.
- `ANALYZE` - собирает статистику для планировщика запросов.
- `VACUUM ANALYZE` - выполняет очистку и сбор статистики.
- `Autovacuum` - автоматически запускает очистку и обновление статистики.
- `FSM` - карта свободного пространства, помогающая PostgreSQL находить страницы для размещения новых данных.
- `Visibility Map` - карта видимости страниц, помогающая, в частности, выполнять `Index Only Scan`.
