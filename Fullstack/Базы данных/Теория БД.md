## Что такое база данных

**База данных (БД)** - структурированное хранилище данных, которым можно управлять и получать из него информацию.

**СУБД** - программа, которая позволяет создавать, изменять и получать данные из БД.

Примеры СУБД:

- PostgreSQL
- MySQL
- SQLite
- MongoDB
- Redis

Основные типы:

- **Реляционные** - PostgreSQL, MySQL
- **NoSQL** - MongoDB, Redis, Cassandra
### Типы СУБД по архитектуре

- **Файл-серверные** - база данных хранится в файле на сервере, а обработка данных выполняется на компьютерах клиентов. Клиент скачивает нужные данные и обрабатывает их локально. При большом количестве пользователей возникают проблемы с производительностью и блокировками. Пример: **Microsoft Access**.
    
- **Клиент-серверные** - база данных хранится на сервере, который самостоятельно обрабатывает SQL-запросы и возвращает клиенту результат. Это снижает сетевой трафик и позволяет централизованно управлять доступом. Примеры: **PostgreSQL, MySQL, Microsoft SQL Server**.
    
- **Встраиваемые** - СУБД работает непосредственно внутри приложения, без отдельного сервера. Данные обычно хранятся в локальном файле, а приложение обращается к ним через библиотеку. Примеры: **SQLite, DuckDB**.
    
**Главное отличие:** в файл-серверной СУБД данные обрабатывает клиент, в клиент-серверной - сервер, а встраиваемая работает внутри приложения.

### Реляционные БД

Данные хранятся в **таблицах**, состоящих из строк и столбцов.
- PostgreSQL
- MySQL
- SQLite
- Oracle

Основные особенности:

- фиксированная схема
- SQL
- связи между таблицами
- JOIN
- транзакции и ACID
- строгие ограничения данных
- хорошо подходят для сложных связанных данных
### Нереляционные БД

**NoSQL** - базы данных, которые не используют классическую табличную реляционную модель.

|Тип|Пример|Использование|
|---|---|---|
|Document|MongoDB|JSON-подобные документы|
|Key-Value|Redis|Кеш, сессии|
|Column|Cassandra|Большие объемы данных|
|Graph|Neo4j|Сложные связи|
Пример из MongoDB:

{
  "id": 1,
  "name": "Oleg",
  "email": "oleg@mail.com",
  "orders": [
    {
      "id": 10,
      "price": 1000
    }
  ]
}

Особенности:

- схема может быть гибкой
- обычно нет необходимости в JOIN как в SQL
- удобно хранить вложенные структуры
- хорошо подходят для горизонтального масштабирования
- модель данных зависит от конкретного типа NoSQL БД

Внутри NoSQL выделяют четыре вида:

### 1. Графовые базы данных

Графовые базы хранят данные в виде узлов и связей между ними. Из графовой базы мы очень быстро можем достать нужные данные — быстрее, чем из реляционной.

### 2. Key-value базы данных

Самый простой формат хранения из всех: есть ключ, есть значение — так информацию и храним.

### 3. Колоночные базы данных

Колоночные базы хранят данные **не построчно**, как реляционные, а **по колонкам**. Это ускоряет аналитику и агрегированные запросы: когда нужна конкретная колонка — посещаемость, количество кликов — такую информацию гораздо проще агрегировать, если она физически лежит вместе.

### 4. Документные базы данных

Даёт возможность хранить информацию неструктурированно. Её сила не в скорости, а в том, что с ней **проще расширяться** — добавлять поля, менять форму документа, не переделывая схему.

| Что храним                           | Куда кладём             | Почему                                                  |
| ------------------------------------ | ----------------------- | ------------------------------------------------------- |
| Сами распарсенные данные             | MongoDB (документная)   | структура каждый раз разная, схему фиксировать не нужно |
| Аналитика по посещаемости            | ClickHouse (колоночная) | агрегаты по колонкам, большие объёмы                    |
| То, что отдаём наружу и нужно быстро | Redis (key-value)       | производительная отдача по ключу                        |
| Связи и маршруты                     | Neo4j (графовая)        | данные сами по себе граф                                |

### Частые вопросы

**Почему индекс ускоряет SELECT?**

Индекс позволяет не искать запись по всей таблице, а использовать специальную структуру данных для быстрого поиска.

**Почему нельзя поставить индекс на все поля?**

Индексы занимают место и замедляют операции записи, потому что их тоже приходится обновлять.

**Чем WHERE отличается от HAVING?**

`WHERE` фильтрует строки до группировки, `HAVING` фильтрует группы после `GROUP BY`.

**Чем DELETE отличается от DROP?**

`DELETE` удаляет строки из таблицы.

`DROP` удаляет сам объект, например таблицу.

**Что такое транзакция?**

Группа операций, которая выполняется как единое целое с соблюдением ACID.

**ACID** - 4 свойства транзакций в реляционных БД:

- **A - Atomicity (атомарность)** - транзакция выполняется целиком или не выполняется вообще.
- **C - Consistency (согласованность)** - после транзакции данные остаются корректными и соблюдают ограничения БД.
- **I - Isolation (изолированность)** - параллельные транзакции не должны некорректно влиять друг на друга.
- **D - Durability (надежность)** - после `COMMIT` изменения сохраняются даже при сбое системы.

Пример с переводом денег: списание денег с одного счета и зачисление на другой должны выполниться **обе операции или ни одна**.

**Что такое индекс?**

Структура данных, которая ускоряет поиск по определенным полям.

**Что такое N+1?**

Ситуация, когда вместо одного эффективного запроса выполняется один запрос на получение списка и отдельный запрос для каждого элемента.

**Зачем нужен Redis?**

Чаще всего для кеширования, хранения сессий, rate limiting и других быстрых временных данных.

**SQL или NoSQL?**

Выбор зависит от модели данных и требований системы. SQL удобен для связанных данных, транзакций и сложных запросов, NoSQL - для сценариев с гибкой структурой или специфическими требованиями к масштабированию.

### Сущности и таблицы

- **Сущность** - объект реального мира или предметной области, информацию о котором нужно хранить в базе данных. Например, пользователь, товар, заказ.
- **Таблица (отношение)** - структура в реляционной БД, состоящая из строк и столбцов, в которой хранятся данные об однотипных объектах. Например, таблица `Users` содержит информацию о пользователях.

**Разница:** сущность - это понятие предметной области, а таблица - способ представить данные о ней в реляционной БД.

**Пример:**

Таблица `Users`:

|id|name|age|
|---|---|---|
|1|Олег|28|
|2|Анна|25|

Здесь:

- `User` - сущность.
- `Users` - таблица, представляющая эту сущность.
- Строка - запись (кортеж) об отдельном пользователе.
- Столбец - атрибут сущности (например, `name`).
- `id` - первичный ключ, уникально идентифицирующий пользователя.

**Результирующий набор** - набор строк и столбцов, возвращаемый СУБД в результате выполнения SQL-запроса.

### PostgreSQL: преимущества и недостатки

**Преимущества:**

- **Бесплатная и открытая** - лицензия PostgreSQL позволяет использовать и модифицировать СУБД без лицензионных отчислений.
- **Соответствие SQL-стандартам** - поддерживает сложные запросы, CTE, оконные функции, транзакции.
- **Надёжность** - ACID-транзакции, MVCC, восстановление после сбоев.
- **Расширяемость** - можно создавать собственные типы данных, функции и расширения.
- **Работа со сложными данными** - поддержка JSON/JSONB, массивов, геоданных через PostGIS.
- **Конкурентный доступ** - MVCC позволяет читать данные без блокировки обычных операций записи.
- **Сложные запросы** - мощные возможности для аналитики и обработки больших объёмов данных.

**Недостатки:**

- **Сложность настройки** - для высокой производительности может потребоваться тонкая настройка конфигурации и запросов.
- **Расход ресурсов** - для небольших задач может быть тяжелее встраиваемых СУБД, например SQLite.
- **Масштабирование** - горизонтальное масштабирование требует дополнительных решений и настройки.
- **Совместимость** - некоторые приложения и инструменты ориентированы на MySQL или Microsoft SQL Server, поэтому миграция может потребовать изменений.
- **Обслуживание** - нужно следить за VACUUM, статистикой, индексами и резервным копированием.

### Краткое сравнение

|СУБД|Главное преимущество|Главное ограничение|
|---|---|---|
|PostgreSQL|Функциональность, расширяемость, сложные запросы|Требует настройки и обслуживания|
|MySQL|Простота освоения, широкое распространение|Некоторые возможности сложной аналитики и SQL отличаются от PostgreSQL|
|SQLite|Лёгкость, отсутствие отдельного сервера|Ограничения при интенсивной конкурентной записи|
|MongoDB|Гибкая документная модель данных|Не всегда удобна для сложных реляционных связей|
|MS SQL Server|Интеграция с экосистемой Microsoft|Коммерческая лицензия для ряда редакций|

**Итого:** PostgreSQL особенно хорош для сложных приложений с реляционными данными, транзакциями и нетривиальными запросами. Для простого локального хранения удобнее SQLite, а выбор между PostgreSQL и MySQL часто зависит от требований проекта и опыта команды.

### Натуральный и суррогатный ключи

**Натуральный ключ** — это поле или набор полей, которые имеют смысл в предметной области и естественным образом идентифицируют запись.

Например, у человека таким ключом может быть номер паспорта, а у страны — код страны.

**Суррогатный ключ** — это искусственно созданный идентификатор, который не несёт предметного смысла и используется для уникальной идентификации записи.

Например, автоматически генерируемый `id`.

### OLAP, OLTP

**OLAP** (online analytical processing, аналитическая обработка) — базы, предназначенные для аналитики и обработки больших объёмов данных. Типичный представитель — Google BigQuery.

**OLTP** (online transaction processing, обработка транзакций в реальном времени) — базы, предназначенные для обработки транзакций в реальном времени и для работы с достаточно внушительным и чувствительным объёмом данных. Простой ориентир: _«всё, что у нас имеет связи, — это OLTP»_. Представители — MySQL и PostgreSQL.

### Способы хранения: persistent, in-memory, embedded

**Persistent** — данные, предназначенные для долгого хранения. (PostgreSQL)

**In-memory** — информация хранится в памяти текущего запущенного инстанса. (Redis)

**Embedded** — встроенные базы данных. Они интегрированы в приложение и работают как его часть. (SQLite) У embedded-подхода есть заметная слабость — безопасность.

# Репликация баз данных

**Репликация — это создание побочной копии.**

у репликации есть конкретные форматы взаимодействия, и их два — master-master и master-slave.

### Master-master: все ведущие

Формат master-master предполагает, что реплик две или больше и **каждая из них ведущая**. Записали на один инстанс — данные должны появиться на другом. Записали на другой — должны появиться на первом. Изменение подтягивается в обе стороны.

### Master-slave: пишем в одну, читаем из другой

Второй формат — master-slave. Схема похожа: тот же балансировщик, тот же сервис, но базы уже не равноправны. Есть **главная база**, куда идёт запись, и **slave-база, которая просто подтягивает изменения**: обращается к мастеру, забирает данные и отдаёт их на чтение через сервис.

|                   | master (command) | slave (query)    |
| ----------------- | ---------------- | ---------------- |
| Основная операция | запись           | чтение           |
| Индексы           | нет              | есть             |
| Что оптимизируем  | скорость вставки | скорость выборки |
### CQRS: команды отдельно, запросы отдельно

**CQRS** — подход, который говорит: разделяйте запись и чтение. **Command** — на внесение данных, **query** — на чтение. Балансировщик направляет запрос по назначению: хочет клиент что-то записать — идёт в сервис с командами; хочет прочитать — идёт в сервис с запросами, а тот уже обращается в базу.
