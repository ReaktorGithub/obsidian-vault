### Реляционные БД

Данные хранятся в **таблицах**, состоящих из строк и столбцов.
- PostgreSQL
- MySQL
- SQLite
- Oracle

Основные особенности:

- фиксированная схема
- SQL
- связи между таблицами
- JOIN
- транзакции и ACID
- строгие ограничения данных
- хорошо подходят для сложных связанных данных
### Нереляционные БД

**NoSQL** - базы данных, которые не используют классическую табличную реляционную модель.

|Тип|Пример|Использование|
|---|---|---|
|Document|MongoDB|JSON-подобные документы|
|Key-Value|Redis|Кеш, сессии|
|Column|Cassandra|Большие объемы данных|
|Graph|Neo4j|Сложные связи|
Пример из MongoDB:

{
  "id": 1,
  "name": "Oleg",
  "email": "oleg@mail.com",
  "orders": [
    {
      "id": 10,
      "price": 1000
    }
  ]
}

Особенности:

- схема может быть гибкой
- обычно нет необходимости в JOIN как в SQL
- удобно хранить вложенные структуры
- хорошо подходят для горизонтального масштабирования
- модель данных зависит от конкретного типа NoSQL БД

## 1. Что такое база данных

**СУБД** - программа, которая позволяет создавать, изменять и получать данные из БД.

Примеры СУБД:

- PostgreSQL
- MySQL
- SQLite
- MongoDB
- Redis

Основные типы:

- **Реляционные** - PostgreSQL, MySQL
- **NoSQL** - MongoDB, Redis, Cassandra

# 2. Реляционная база данных

В реляционной БД данные хранятся в **таблицах**.

Например:

```
users
```

|id|name|email|
|---|---|---|
|1|Oleg|[oleg@mail.com](mailto:oleg@mail.com)|
|2|Ivan|[ivan@mail.com](mailto:ivan@mail.com)|

Таблица состоит из:

- **строк (row)** - отдельные записи
- **столбцов (column)** - свойства записи
- **ячеек** - конкретные значения

---

# 3. Первичный ключ

**Primary Key (PK)** - уникальный идентификатор записи.

```
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  email VARCHAR(255)
);
```

`id`:

- уникальный
- не может быть `NULL`
- однозначно определяет запись

Обычно используется `id`.

---

# 4. Внешний ключ

**Foreign Key (FK)** связывает одну таблицу с другой.

Например:

```
users
id
name
```

```
orders
id
user_id
price
```

`orders.user_id` ссылается на `users.id`.

```
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),
  price INTEGER
);
```

Это связь:

```
User 1 ---- N Orders
```

Один пользователь может иметь много заказов.

---

# 5. Типы связей

## One-to-One

Одна запись соответствует одной записи.

```
User 1 ---- 1 Passport
```

Например:

```
users
user_id

passports
user_id
```

## One-to-Many

Одна запись соответствует нескольким.

```
User 1 ---- N Orders
```

Самая распространенная связь.

## Many-to-Many

Много записей связаны с множеством других.

Например:

```
Users N ---- N Roles
```

Обычно создается промежуточная таблица:

```
users
roles
user_roles
```

```
user_roles

user_id
role_id
```

# 7. SELECT

Получить данные:

```
SELECT * FROM users;
```

Конкретные поля:

```
SELECT id, name
FROM users;
```

С условием:

```
SELECT *
FROM users
WHERE age > 18;
```

Несколько условий:

```
SELECT *
FROM users
WHERE age > 18
  AND city = 'Moscow';
```

---

# 8. INSERT

Добавление записи:

```
INSERT INTO users (name, email)
VALUES ('Oleg', 'oleg@mail.com');
```

Несколько записей:

```
INSERT INTO users (name, email)
VALUES
  ('Oleg', 'oleg@mail.com'),
  ('Ivan', 'ivan@mail.com');
```

---

# 9. UPDATE

Изменение:

```
UPDATE users
SET name = 'Alex'
WHERE id = 1;
```

Важно:

```
UPDATE users
SET name = 'Alex';
```

Изменит **всех пользователей**.

Поэтому обычно нужен `WHERE`.

---

# 10. DELETE

```
DELETE FROM users
WHERE id = 1;
```

Без `WHERE`:

```
DELETE FROM users;
```

удалит все записи.

---

# 11. NULL

`NULL` означает отсутствие значения.

Важно:

```
WHERE name = NULL
```

неправильно.

Используется:

```
WHERE name IS NULL
```

или:

```
WHERE name IS NOT NULL
```

`NULL` не равен:

```
0
''
false
```

# 12. JOIN

`JOIN` используется для получения данных из нескольких таблиц.

Например:

```
users
id
name
```

```
orders
id
user_id
price
```

Получить пользователя и его заказы:

```
SELECT users.name, orders.price
FROM users
JOIN orders
  ON users.id = orders.user_id;
```

---

## INNER JOIN

Возвращает только записи, у которых есть соответствие в обеих таблицах.

```
SELECT *
FROM users
INNER JOIN orders
  ON users.id = orders.user_id;
```

Если у пользователя нет заказов, он не попадет в результат.

---

## LEFT JOIN

Возвращает все записи из левой таблицы.

```
SELECT *
FROM users
LEFT JOIN orders
  ON users.id = orders.user_id;
```

Даже если у пользователя нет заказов.

Тогда поля `orders` будут `NULL`.

Частый вопрос на собеседовании:

> Чем INNER JOIN отличается от LEFT JOIN?

**INNER JOIN** - только совпавшие записи.

**LEFT JOIN** - все записи слева + совпадения справа.

# 13. GROUP BY

Группирует записи.

Например, количество заказов каждого пользователя:

```
SELECT user_id, COUNT(*)
FROM orders
GROUP BY user_id;
```

Другие агрегатные функции:

```
COUNT()
SUM()
AVG()
MIN()
MAX()
```

Например:

```
SELECT user_id, SUM(price)
FROM orders
GROUP BY user_id;
```

---

# 14. HAVING

`WHERE` фильтрует отдельные записи.

`HAVING` фильтрует группы.

```
SELECT user_id, COUNT(*)
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 5;
```

Получим пользователей, у которых больше 5 заказов.

# 17. Индексы

**Индекс** - структура данных, которая ускоряет поиск по таблице.

Без индекса БД может сделать:

```
Full Table Scan
```

То есть пройти по всем строкам.

Например:

```
SELECT *
FROM users
WHERE email = 'oleg@mail.com';
```

Если `email` индексирован, поиск будет быстрее.

Создание:

```
CREATE INDEX idx_users_email
ON users(email);
```

---

## Почему не создать индекс на каждом поле?

Индексы:

- занимают место
- замедляют `INSERT`
- замедляют `UPDATE`
- замедляют `DELETE`

При изменении данных индекс тоже нужно обновлять.

Поэтому индексируют поля, по которым часто выполняются:

```
WHERE
JOIN
ORDER BY
```

---

# 18. Составной индекс

Индекс может содержать несколько полей:

```
CREATE INDEX idx_users_city_age
ON users(city, age);
```

Порядок полей имеет значение.

Такой индекс хорошо подходит для запросов:

```
WHERE city = 'Moscow'
```

и:

```
WHERE city = 'Moscow'
AND age > 20
```

Но не обязательно эффективно используется для:

```
WHERE age > 20
```

---

# 19. Уникальный индекс

Гарантирует уникальность значения:

```
CREATE UNIQUE INDEX idx_users_email
ON users(email);
```

Теперь два пользователя не смогут иметь одинаковый email.

Часто это задается через:

```
email VARCHAR(255) UNIQUE
```

---

# 20. Нормализация

**Нормализация** - организация данных таким образом, чтобы уменьшить дублирование и проблемы с обновлением.

Плохо:

```
orders

id
user_name
user_email
product_name
product_price
```

Информация о пользователе дублируется в каждом заказе.

Лучше:

```
users
id
name
email
```

```
orders
id
user_id
```

```
products
id
name
price
```

---

# 21. Денормализация

**Денормализация** - намеренное дублирование данных ради производительности или упрощения чтения.

Например, вместо постоянного JOIN хранить:

```
orders

id
user_id
user_name
total_price
```

Плюсы:

- меньше JOIN
- быстрее чтение

Минусы:

- дублирование
- сложнее поддерживать актуальность данных

Используется, когда производительность чтения важнее строгой нормализации.

---

# 22. Транзакции

**Транзакция** - группа операций, которая выполняется как единое целое.

Например, перевод денег:

```
Списать 100 ₽ у A
        +
Добавить 100 ₽ B
```

Обе операции должны выполниться.

Если первая прошла, а вторая нет, данные становятся некорректными.

```
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

Если произошла ошибка:

```
ROLLBACK;
```

---

# 23. ACID

Свойства транзакций.

### Atomicity

**Атомарность**

Транзакция выполняется целиком или не выполняется вообще.

```
Все операции
или
ни одной
```

### Consistency

**Согласованность**

После транзакции БД остается в корректном состоянии.

### Isolation

**Изолированность**

Параллельные транзакции не должны некорректно влиять друг на друга.

### Durability

**Надежность**

После `COMMIT` изменения не должны потеряться.

---

# 24. Проблемы параллельных транзакций

При одновременной работе нескольких транзакций могут возникать:

### Dirty Read

Одна транзакция читает незакоммиченные изменения другой.

```
Transaction A -> изменяет данные
Transaction B -> читает их
Transaction A -> ROLLBACK
```

B прочитала данные, которых фактически не существует.

### Non-Repeatable Read

Один и тот же запрос внутри транзакции возвращает разные данные.

### Phantom Read

Повторный запрос возвращает новые или исчезнувшие строки.

# 25. Уровни изоляции

Основные:

```
READ UNCOMMITTED
READ COMMITTED

```

Чем выше изоляция:

Основные:

```
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
```

Пример:


# 27. CASCADE

Определяет поведение при удалении или изменении связанной записи.

Например:

```
user_id INTEGER
REFERENCES users(id)
ON DELETE CASCADE
```

Если удалить пользователя, связанные заказы тоже будут удалены.

Важно использовать осторожно, потому что можно удалить большое количество связанных данных.

# 28. View

**View** - сохраненный SQL-запрос, который выглядит как таблица.

```
CREATE VIEW active_users AS
SELECT *
FROM users
WHERE active = true;
```

Использование:

```
SELECT *
FROM active_users;
```

Данные обычно не копируются. При обращении выполняется запрос, лежащий за представлением.

# 30. Pagination

Не стоит загружать тысячи записей сразу.

Простой вариант:

```
SELECT *
FROM users
LIMIT 20
OFFSET 40;
```

Получаем третью страницу по 20 элементов.

Проблема `OFFSET` - на больших таблицах БД может тратить много ресурсов на пропуск строк.

Для больших данных используют **cursor/keyset pagination**:

```
SELECT *
FROM users
WHERE id > 1000
ORDER BY id
LIMIT 20;
```

Это обычно эффективнее на больших таблицах.

---

# 31. SQL Injection

Опасный вариант:

```
const query = `
  SELECT *
  FROM users
  WHERE email = '${email}'
`;
```

Пользователь может передать SQL-код.

Используют параметризованные запросы:

```
db.query(
  'SELECT * FROM users WHERE email = $1',
  [email]
);
```

ORM также обычно предоставляет безопасные механизмы параметризации.

# 32. ORM

**ORM (Object-Relational Mapping)** связывает объекты приложения с таблицами БД.

Например:

```
User class
    ↓
users table
```

Примеры:

- Prisma
- TypeORM
- Sequelize
- MikroORM

Вместо:

```
SELECT * FROM users WHERE id = 1;
```

можно писать:

```
prisma.user.findUnique({
  where: { id: 1 }
});
```

Плюсы:

- меньше ручного SQL
- типизация
- удобная работа с сущностями
- миграции
- связи между моделями

Минусы:

- абстракция может скрывать реальную стоимость запросов
- сложные запросы иногда проще написать на SQL
- неправильное использование ORM может привести к N+1 и лишним запросам

---

# 33. N+1 Query Problem

Например, получили 100 пользователей:

```
SELECT * FROM users;
```

А затем для каждого пользователя отдельно получили заказы:

```
1 запрос пользователей
+
100 запросов заказов
=
101 запрос
```

Это проблема **N+1**.

Решение:

- `JOIN`
- eager loading
- batch loading
- DataLoader
- оптимизация ORM-запроса

# 34. SQL vs NoSQL

## SQL

Примеры:

```
PostgreSQL
MySQL
```

Подходит, когда:

- четкая структура данных
- нужны связи
- нужны транзакции
- сложные запросы
- важна согласованность

## NoSQL

Примеры:

```
MongoDB
Redis
Cassandra
```

Подходит для задач, где удобнее:

- гибкая структура
- высокая скорость определенных операций
- горизонтальное масштабирование
- хранение документов или key-value данных

Выбор зависит от задачи, а не от принципа "NoSQL быстрее SQL".

# 35. MongoDB

MongoDB - документная NoSQL БД.

Вместо таблиц используются:

```
Database
  ↓
Collection
  ↓
Document
```

Пример:

```
{
  "_id": "123",
  "name": "Oleg",
  "email": "oleg@mail.com"
}
```

Документ может содержать вложенные данные:

```
{
  "name": "Oleg",
  "address": {
    "city": "Moscow",
    "street": "Lenina"
  }
}
```

# 36. Redis

Redis - быстрое in-memory хранилище типа key-value.

```

```

Например:

```

```

Часто используется для:

- кеширования
- сессий
- rate limiting
- временных данных
- очередей
- распределенных блокировок

Пример кеша:

```
Request
   ↓
Redis
   ↓
если нет данных
   ↓
Database
```

# 37. Репликация

**Replication** - создание копий БД.

Например:

```
          Primary
         /       \
    Replica     Replica
```

Запись идет в Primary.

Чтение можно распределять между Replica.

Плюсы:

- масштабирование чтения
- отказоустойчивость
- резервирование

Минус - реплики могут отставать от Primary.

Это называется **replication lag**.

---

# 38. Шардирование

**Sharding** - разделение данных между несколькими серверами.

Например:

```
Shard 1 -> users 1-1 000 000
Shard 2 -> users 1 000 001-2 000 000
Shard 3 -> users 2 000 001-3 000 000
```

Используется для горизонтального масштабирования очень больших объемов данных.

Главная проблема - правильный выбор **shard key**.

---

# 39. Backup

**Backup** - резервная копия данных.

Нужен для восстановления после:

- удаления данных
- ошибки приложения
- сбоя сервера
- повреждения БД
- атаки

Важно не только создавать backup, но и регулярно проверять, что из него реально можно восстановиться.

---

# 40. Миграции

**Migration** - версионирование изменений структуры БД.

Например:

```
001_create_users
002_create_orders
003_add_user_avatar
004_add_index_email
```

Миграции позволяют одинаково изменять структуру БД на:

```
development
staging
production
```

---

# 41. Что происходит при SQL-запросе

Упрощенно:

```
Application
     ↓
SQL query
     ↓
Parser
     ↓
Query Planner
     ↓
Execution
     ↓
Indexes / Tables
     ↓
Result
```

**Query Planner** выбирает способ выполнения запроса.

Например, решить:

```
использовать индекс
```

или:

```
просканировать таблицу
```

Поэтому наличие индекса не гарантирует, что БД всегда его использует.

# 42. EXPLAIN

```
EXPLAIN
```

Например:

```
EXPLAIN
```

Можно посмотреть, как БД планирует выполнять запрос.

Часто используется:

### Частые вопросы

**Почему индекс ускоряет SELECT?**

Индекс позволяет не искать запись по всей таблице, а использовать специальную структуру данных для быстрого поиска.

**Почему нельзя поставить индекс на все поля?**

Индексы занимают место и замедляют операции записи, потому что их тоже приходится обновлять.

**Чем WHERE отличается от HAVING?**

`WHERE` фильтрует строки до группировки, `HAVING` фильтрует группы после `GROUP BY`.

**Чем DELETE отличается от DROP?**

`DELETE` удаляет строки из таблицы.

`DROP` удаляет сам объект, например таблицу.

**Что такое транзакция?**

Группа операций, которая выполняется как единое целое с соблюдением ACID.

**ACID** - 4 свойства транзакций в реляционных БД:

- **A - Atomicity (атомарность)** - транзакция выполняется целиком или не выполняется вообще.
- **C - Consistency (согласованность)** - после транзакции данные остаются корректными и соблюдают ограничения БД.
- **I - Isolation (изолированность)** - параллельные транзакции не должны некорректно влиять друг на друга.
- **D - Durability (надежность)** - после `COMMIT` изменения сохраняются даже при сбое системы.

Пример с переводом денег: списание денег с одного счета и зачисление на другой должны выполниться **обе операции или ни одна**.

**Что такое индекс?**

Структура данных, которая ускоряет поиск по определенным полям.

**Что такое N+1?**

Ситуация, когда вместо одного эффективного запроса выполняется один запрос на получение списка и отдельный запрос для каждого элемента.

**Зачем нужен Redis?**

Чаще всего для кеширования, хранения сессий, rate limiting и других быстрых временных данных.

**SQL или NoSQL?**

Выбор зависит от модели данных и требований системы. SQL удобен для связанных данных, транзакций и сложных запросов, NoSQL - для сценариев с гибкой структурой или специфическими требованиями к масштабированию.
