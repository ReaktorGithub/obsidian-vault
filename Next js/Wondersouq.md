**Как был устроен Next.js на проекте:**

> Next.js использовали как основной фреймворк для клиентской части поверх React. Приложение было разделено на публичную часть - каталог, магазины, карточки товаров, авторизацию - и административную панель для владельцев магазинов.
> 
> Для страниц, где данные могли меняться редко, использовали серверный рендеринг или предварительную генерацию. Динамические данные, например корзина, пользовательские настройки и состояние 3D-сцены, загружались на клиенте через API и GraphQL.
> 
> Next.js отвечал за маршрутизацию, структуру страниц, загрузку данных и оптимизацию первоначальной загрузки. При этом сам 3D-контент рендерился на клиенте через Three.js, поэтому такие компоненты подключались с отключенным SSR, чтобы не было проблем с `window`, WebGL и DOM.
> 
> Для тяжелых компонентов использовали динамический импорт и code splitting. Например, 3D-сцену, админские модули и некоторые тяжелые таблицы не загружали в первоначальный bundle, если они не требовались пользователю сразу.
> 
> Авторизация была связана с Amazon Cognito. После входа пользователь получал данные сессии, а защищенные страницы и API-запросы работали с учетом авторизации пользователя.
> 
> Также Next.js использовали вместе с CDN для отдачи статических ресурсов и оптимизации загрузки. Основное внимание уделяли LCP и времени до интерактивности, особенно из-за большого количества 3D-ассетов.

### Если спросят конкретно: «Что именно делал Next.js?»

Можно ответить короче:

> Next.js был основой приложения: роутинг, страницы, SSR/клиентский рендеринг, динамические импорты и code splitting. Основная бизнес-логика была на React, а Next.js помогал организовать приложение и оптимизировать загрузку. Для Three.js использовали client-only компоненты, потому что WebGL и `window` недоступны на сервере.

### Если спросят «Почему не просто React?»

> Нам был нужен не только React, а полноценный framework для большого приложения. Next.js давал готовую маршрутизацию, серверный рендеринг, code splitting, оптимизацию загрузки и удобную работу с CDN. При этом интерактивная часть и 3D-сцены оставались обычными React-компонентами.

### Важный момент про 3D

На собеседовании это особенно хорошо звучит:

> 3D-сцена была отдельным клиентским слоем. Мы не пытались рендерить Three.js на сервере. Next.js отдавал страницу и необходимый 2D-интерфейс, а после загрузки клиент инициализировал Three.js-сцену. Между ними было состояние, через которое, например, выбор магазина или товара в 2D-интерфейсе мог менять объект или состояние сцены.

**Упрощённая архитектура:**

```
Next.js
   │
   ├── Роутинг
   ├── SSR / Client Rendering
   ├── Code Splitting
   ├── Авторизация
   │
   ├── React UI
   │    ├── Каталог
   │    ├── Корзина
   │    ├── Формы
   │    └── Admin Panel
   │
   └── 3D слой
        └── Three.js / WebGL
              ↕
        состояние React
```
