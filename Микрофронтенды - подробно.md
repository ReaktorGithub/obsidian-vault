**Архитектура frontend-приложений: от монолита до Microfrontends**

**1. Монолитный фронтенд**

**Монолитный фронтенд** - это frontend-приложение, в котором весь функционал находится внутри одного приложения, собирается как единое целое и обычно деплоится одним артефактом.

**Артефакт** в разработке - это **результат сборки проекта, который можно передать дальше: задеплоить, запустить или опубликовать**.

·  **Исходный код** → то, что пишут разработчики.

·  **Сборка** → процесс превращения исходного кода в готовые файлы.

·  **Артефакт** → результат этой сборки.

·  **Деплой** → размещение артефакта на сервере или в другом окружении.

Упрощенно:

Git repository

└── frontend

    ├── src

    │   ├── pages

    │   ├── components

    │   ├── features

    │   └── ...

    ├── package.json

    └── ...

Например, интернет-магазин:

Frontend

├── auth

├── catalog

├── cart

├── orders

├── payments

└── profile

Все эти части являются частью **одного frontend-приложения**.

**Важно**

Монолитность определяется не количеством репозиториев или команд, а прежде всего тем, что приложение является **единым deployable unit** и имеет единый runtime.

**Deployable unit** - это **минимальная самостоятельная единица, которую можно отдельно развернуть в окружении**. Проще говоря: если часть приложения нельзя задеплоить отдельно, а нужно обязательно выкатывать вместе со всем приложением, то они находятся в одном deployable unit.

Поэтому:

- один репозиторий - не обязательное условие;
- одна команда - не обязательное условие;
- один процесс сборки - типичный признак, но не строгая архитектурная характеристика.

**Проблемы монолита при росте**

Пока приложение небольшое, монолитная архитектура часто является оптимальным вариантом.

С ростом продукта:

Небольшой проект

      ↓

Больше функционала

      ↓

Больше разработчиков

      ↓

Больше бизнес-модулей

      ↓

Больше зависимостей

      ↓

Сложнее изменения и релизы

Например, команда каталога изменила общую библиотеку компонентов. Из-за этого необходимо проверить и собрать всё приложение.

Или команда платежей хочет быстро выкатить изменение, но не может сделать это независимо от остальных частей приложения.

**Плюсы**

- Простая разработка и локальный запуск.
- Простая сборка и деплой.
- Относительно легко организовать общие зависимости.
- Проще отлаживать взаимодействие между частями приложения.
- Меньше инфраструктурной сложности.

**Минусы**

- С увеличением кодовой базы усложняется поддержка.
- Изменения могут затрагивать всё приложение.
- Один релиз может требовать координации нескольких команд.
- Сложнее независимо масштабировать команды.
- Большое количество зависимостей может приводить к сильной связанности.

**2. Модульный монолит**

**Модульный монолит** - это единое приложение, которое внутри разделено на крупные модули с четкими границами и ответственностями.

Главная идея:

**Один deployable unit, но внутри него несколько хорошо изолированных бизнес-модулей.**

Например:

Frontend

├── auth

├── catalog

├── cart

├── orders

├── payments

└── profile

Каждый модуль отвечает за свою бизнес-область.

Например:

orders

├── pages

├── features

├── entities

└── api

При этом модули могут использовать общий код:

shared

├── ui

├── hooks

├── utils

└── api

**Главное отличие от обычного монолита**

Обычный монолит может постепенно превратиться в:

components/

├── Button

├── UserCard

├── OrderCard

├── ...

├── OrderButton

├── PaymentButton

└── ...

где зависимости между бизнес-областями становятся хаотичными.

В модульном монолите стараются установить правила:

orders → может использовать shared

orders → может использовать определенные публичные API других модулей

orders ✕ → не лезет напрямую во внутренности payments

То есть модули имеют **границы и публичные интерфейсы**.

**Как это выглядит с точки зрения деплоя?**

Обычно:

Git repository

      ↓

одна сборка

      ↓

один frontend artifact

      ↓

один деплой

То есть это всё еще **один frontend**.

Может быть несколько репозиториев, несколько команд и даже несколько pipeline, но если результатом остается одно приложение, которое деплоится как единое целое, это не превращает его автоматически в microfrontends.

На практике модульный монолит чаще всего удобно держать **в одном репозитории**.

**Пример с несколькими командами**

Допустим, есть 4 команды:

Команда A → Catalog

Команда B → Orders

Команда C → Payments

Команда D → Profile

Все работают над одним приложением:

                Frontend

                   │

       ┌───────────┼───────────┐

       ↓           ↓           ↓

    Catalog      Orders     Payments

       │           │           │

       └───────────┼───────────┘

                   ↓

                Shared

Команды могут независимо работать внутри своих модулей, но в конце всё собирается в одно приложение.

**Как это настраивается технически?**

Например, можно организовать проект через feature/domain boundaries:

src/

├── modules/

│   ├── catalog/

│   ├── orders/

│   ├── payments/

│   └── profile/

│

├── shared/

│   ├── ui/

│   ├── lib/

│   └── api/

│

└── app/

Дополнительно архитектурные границы можно контролировать:

- ESLint rules;
- TypeScript path aliases;
- dependency rules;
- Nx или Turborepo;
- архитектурными линтерами;
- code review.

**Плюсы**

- Понятное разделение бизнес-областей.
- Проще распределять ответственность между командами.
- Можно переиспользовать общий код.
- Относительно простая инфраструктура.
- Нет необходимости сразу внедрять microfrontends.

**Минусы**

- Всё еще единый runtime.
- Обычно единый build и deploy.
- Команды зависят от общей кодовой базы.
- Изменения в shared-коде могут затрагивать всех.
- С ростом количества команд границы начинают становиться недостаточными.

**3. Монорепозиторий**

**Монорепозиторий (monorepo)** - это один Git-репозиторий, в котором находится несколько проектов, приложений и пакетов.

Главное:

**Monorepo - это способ организации кода, а не frontend-архитектура сам по себе.**

В monorepo можно хранить как обычные монолиты, так и microfrontends.

Например:

monorepo/

├── apps/

│   ├── customer-portal/

│   ├── admin/

│   ├── analytics/

│   └── mobile-web/

│

└── packages/

    ├── ui/

    ├── eslint-config/

    ├── ts-config/

    ├── api-client/

    └── utils/

**Apps**

apps содержит самостоятельные приложения.

Например:

apps/

├── customer-portal/

│   └── src/

│

├── admin/

│   └── src/

│

└── analytics/

    └── src/

Каждое приложение может иметь:

- свой package.json;
- свой src;
- свои зависимости;
- свой build;
- свой deploy.

**Packages**

packages содержит код, который переиспользуется несколькими приложениями.

Например:

packages/

├── ui/

├── api-client/

├── eslint-config/

├── ts-config/

└── utils/

Тогда:

customer-portal ──┐

admin ────────────┼──→ packages/ui

analytics ────────┘

**Что происходит при росте продукта?**

Например, вместо одного большого frontend появляются отдельные приложения:

                 Monorepo

                    │

       ┌────────────┼────────────┐

       ↓            ↓            ↓

   Customer       Admin       Analytics

Это уже позволяет разделить приложения и команды:

Команда A → customer-portal

Команда B → admin

Команда C → analytics

При этом команды могут использовать общий код.

**Плюсы**

- Несколько приложений в одном месте.
- Общие библиотеки и конфигурации.
- Удобный рефакторинг между проектами.
- Единый dependency management.
- Удобно организовывать ownership.
- Можно запускать CI только для затронутых приложений.

**Ownership** в разработке - это **ответственность за определённую часть продукта или кода**.

**Минусы**

- Репозиторий становится большим.
- Много бизнес-направлений могут оказаться в одном месте.
- Общие packages становятся критической точкой связанности.
- Изменение shared-кода может затронуть много приложений.
- Требуется хорошая настройка CI, dependency management и ownership.

**Как настраивается технически?**

Для monorepo часто используют:

- **Turborepo**;
- **Nx**;
- pnpm workspaces;
- npm workspaces;
- Yarn workspaces.

Например, с Turborepo:

apps/

packages/

turbo.json

package.json

pnpm-workspace.yaml

Turborepo помогает управлять задачами между приложениями и пакетами:

build

test

lint

typecheck

и запускать их только там, где это необходимо.

Workspace - это логическая группа пакетов внутри монорепозитория, которую пакетный менеджер умеет устанавливать, связывать и собирать как единое пространство.

# pnpm-workspace.yaml

packages:

  - "apps/*"

  - "packages/*"

# package.json

{

  "name": "my-monorepo",

  "private": true,

  "scripts": {

    "build": "pnpm -r build"

  }

}

**4. Выделение контуров**

Когда продукт становится очень большим, одного monorepo может быть недостаточно.

Например, есть большая компания:

Компания

├── Интернет-магазин

├── Банковские продукты

├── B2B

├── Логистика

└── Внутренние системы

Каждое направление становится отдельным **контуром**.

Под контуром здесь можно понимать **изолированную область разработки и ответственности**, которая объединяет связанные приложения и команды.

Например:

Контур Commerce

├── Customer Portal

├── Admin

└── Analytics

Контур Logistics

├── Warehouse

├── Delivery

└── Tracking

У каждого контура может быть собственный monorepo:

commerce/

├── apps/

└── packages/

logistics/

├── apps/

└── packages/

Таким образом:

                Компания

                   │

        ┌──────────┼──────────┐

        ↓          ↓          ↓

    Commerce    Logistics    B2B

        │          │          │

      Monorepo   Monorepo   Monorepo

**Что дает выделение контуров?**

У каждого направления могут быть:

- собственный roadmap;
- свои команды;
- свои процессы;
- собственный CI/CD;
- собственные релизы;
- свои правила разработки;
- собственные инфраструктурные решения.

Связность между бизнес-направлениями уменьшается.

**Но появляется новая проблема**

Внутри каждого контура снова может вырасти огромный frontend:

Commerce

└── Monorepo

    ├── Customer Portal

    ├── Admin

    ├── Catalog

    ├── Checkout

    ├── Orders

    └── ...

Теперь бизнесы разделены, но внутри одного бизнеса снова появляется большое приложение и большое количество команд.

**5. Microfrontends**

**Microfrontend** - архитектурный подход, при котором frontend-приложение разделяется на несколько относительно независимых частей, каждая из которых может разрабатываться и поставляться независимо.

Главная идея:

**Разделить не только код, но и ответственность, ownership и жизненный цикл отдельных частей frontend.**

Например:

                 Shell

                   │

       ┌───────────┼───────────┐

       ↓           ↓           ↓

    Catalog      Cart       Profile

       │           │           │

     Team A      Team B      Team C

Каждый microfrontend отвечает за определенную бизнес-область.

Например:

Catalog MF

Checkout MF

Orders MF

Profile MF

**Важное отличие от модульного монолита**

В модульном монолите:

Modules

   ↓

одна сборка

   ↓

один deploy

В microfrontends:

MF A ──→ свой build

MF B ──→ свой build

MF C ──→ свой build

Части приложения могут иметь **независимый жизненный цикл**.

Но microfrontend не обязательно означает отдельный репозиторий. Он может находиться в monorepo или multirepo.

**Плюсы:**

- **Независимый деплой** - команды могут выкатывать свои части приложения отдельно.
- **Независимая разработка** - разные команды могут работать над своими доменами, не затрагивая весь проект.
- **Изоляция** - ошибка или изменение одного микрофронтенда меньше влияет на остальные.
- **Автономность команд** - команда имеет ownership над своей частью продукта.
- **Разные технологии** - при необходимости микрофронтенды могут использовать разные версии библиотек или даже разные фреймворки.
- **Масштабирование команд** - удобно для больших продуктов с большим количеством команд.

**Минусы:**

- **Сложнее архитектура** - нужно решать вопросы интеграции, маршрутизации, shared-зависимостей и коммуникации между частями.
- **Сложнее сборка и деплой** - появляется несколько пайплайнов и deployable units.
- **Дублирование зависимостей** - например, несколько микрофронтендов могут загрузить свои копии React.
- **Сложнее shared state** - взаимодействие между микрофронтендами требует дополнительных решений.
- **Сложнее debugging** - ошибку иногда приходится искать на границе нескольких приложений.
- **Производительность** - неправильная организация может увеличить размер бандла и количество сетевых запросов.
- **Больше инфраструктуры** - CI/CD, versioning, мониторинг, runtime-интеграция.

**Module Federation**

**Module Federation** - технология, которая позволяет одному JavaScript-приложению загружать модули из другого приложения **во время выполнения**.

Она особенно часто используется для реализации microfrontends.

Например:

Shell

  │

  ├── загружает Catalog MF

  ├── загружает Cart MF

  └── загружает Profile MF

Условно:

Shell

  ↓

remoteEntry.js

  ↓

Catalog

  ↓

Catalog components

Shell не обязательно должен содержать весь код Catalog во время собственной сборки.

**Пример**

Есть два приложения:

host/

remote-catalog/

remote-catalog предоставляет:

ProductList

ProductCard

А host подключает их:

const ProductList = lazy(

  () => import('catalog/ProductList')

);

Конкретный API зависит от версии Module Federation и используемого bundler.

**Что дает Module Federation?**

- Runtime-загрузка модулей.
- Независимая сборка remote-приложений.
- Возможность обновлять отдельные части приложения.
- Возможность разделять ownership между командами.

**Module Federation - не единственный способ реализации Microfrontends**

Другие подходы:

**1. Runtime composition**

Части приложения объединяются во время выполнения.

Например:

Shell

 ↓

MF A

MF B

MF C

Module Federation - один из способов такой композиции.

**2. Build-time composition**

Microfrontend подключается как npm package:

catalog-package

      ↓

Shell build

      ↓

готовое приложение

Это проще, но изменения требуют пересборки host.

**3. Server-side composition**

Сервер собирает страницу из независимых frontend-фрагментов.

Browser

   ↓

Server

 ├── Catalog

 ├── Cart

 └── Profile

**4. Web Components**

Microfrontend предоставляет UI в виде Web Component:

<catalog-widget></catalog-widget>

Это позволяет уменьшить зависимость от конкретного frontend-фреймворка.

**Важный момент**

**Microfrontends и Module Federation - не одно и то же.**

Microfrontends - **архитектурный подход**.

Module Federation - **одна из технологий**, с помощью которой этот подход можно реализовать.

**6. Microfrontends + Monorepo**

Можно объединить несколько microfrontends в одном monorepo.

Например:

commerce/

├── apps/

│   ├── shell/

│   ├── catalog/

│   ├── checkout/

│   └── profile/

│

└── packages/

    ├── ui/

    ├── eslint-config/

    └── api-client/

Здесь:

shell       → Host

catalog     → Microfrontend

checkout    → Microfrontend

profile     → Microfrontend

При этом они находятся в **одном** **Git-****репозитории**.

Каждая команда может владеть своим приложением:

Team A → catalog

Team B → checkout

Team C → profile

Team D → shell

**Как происходит сборка?**

Например:

catalog

   ↓

build

   ↓

remote

checkout

   ↓

build

   ↓

remote

profile

   ↓

build

   ↓

remote

Shell знает, где находятся эти remote-приложения, и подключает их.

**Плюсы**

- Один пользовательский опыт.
- Независимые части приложения.
- Разделение ownership.
- Команды могут независимо развивать свои области.
- Общий monorepo упрощает работу с shared-кодом.
- Удобно делать общие tooling и CI.

**Минусы**

- Команды всё еще находятся в одном репозитории.
- Shared packages создают связанность.
- Общие зависимости требуют координации.
- CI/CD становится сложнее.
- Нужно управлять совместимостью между microfrontends.
- Большое количество команд может создавать организационные конфликты.

**7. Microfrontends + Multirepo**

Следующий уровень изоляции - отдельный репозиторий для каждого microfrontend.

Git

├── shell-repo

├── catalog-repo

├── checkout-repo

├── profile-repo

└── orders-repo

Каждая команда получает максимально самостоятельный lifecycle:

Catalog Team

├── свой repository

├── свой CI/CD

├── свои зависимости

├── свой release

└── свой deployment

Архитектура:

                    Shell

                      │

        ┌─────────────┼─────────────┐

        ↓             ↓             ↓

    Catalog        Checkout       Profile

      Repo            Repo           Repo

        │             │             │

      Team A         Team B         Team C

Shell объединяет эти части в единое пользовательское приложение.

**Плюсы**

- Максимальная автономность команд.
- Независимые CI/CD.
- Независимые релизы.
- Независимые lifecycle.
- Можно выбирать технологии независимо.
- Изменения одного MF не требуют пересборки остальных.
- Разные команды могут иметь разные процессы разработки.

**Минусы**

- Значительно сложнее инфраструктура.
- Нужно управлять контрактами между MF.
- Сложнее управлять версиями.
- Больше CI/CD pipeline.
- Сложнее локальная разработка.
- Сложнее debugging.
- Возможны проблемы совместимости.
- Нужно отдельно решать вопрос shared UI и shared dependencies.

Главная проблема становится такой:

**Мы получили максимальную независимость, но заплатили за нее сложностью распределенной системы.**

---

**Как развивалась архитектура**

Эту эволюцию удобно запомнить как постепенное разделение ответственности.

Монолит

   ↓

Разделяем код

   ↓

Модульный монолит

   ↓

Разделяем приложения

   ↓

Monorepo

   ↓

Разделяем бизнес-направления

   ↓

Контуры

   ↓

Разделяем frontend внутри бизнеса

   ↓

Microfrontends

   ↓

Разделяем репозитории

   ↓

Microfrontends + Multirepo

При этом это **не обязательная последовательность**, через которую должен пройти каждый проект.

Можно сразу построить monorepo. Можно вообще не переходить к microfrontends. Можно использовать monorepo и microfrontends одновременно.

---

**Главное различие подходов**

|**Подход**|**Основная единица**|**Репозиторий**|**Деплой**|
|---|---|---|---|
|Монолит|Одно приложение|Обычно один|Обычно один|
|Модульный монолит|Модули внутри приложения|Обычно один|Обычно один|
|Monorepo|Несколько приложений и packages|Один|Может быть разным для каждого app|
|Контуры|Бизнес-направления|Несколько monorepo|Независимый по контурам|
|Microfrontends|Независимые frontend-части|Один или несколько|Может быть независимым|
|MF + Multirepo|Независимые MF|Отдельный repo на MF|Независимый|

**Ключевой момент:** monorepo, multirepo и microfrontends отвечают на разные вопросы.

- **Monorepo / multirepo** - как организован исходный код.
- **Модульный монолит / microfrontends** - как организована архитектура приложения.
- **CI/CD и deployment** - как части системы собираются и поставляются.
- **Module Federation** - одна из технологий runtime-композиции microfrontends.

Поэтому вполне возможна такая комбинация:

Monorepo

   +

Microfrontends

   +

Module Federation

   +

Independent CI/CD

   +

Independent deployment

И наоборот, **microfrontend не обязан использовать Module Federation и не обязан находиться в отдельном репозитории**.

**Микросервисы**

**Микросервисы** - это архитектурный подход, при котором backend разбивается на **небольшие независимые сервисы**, каждый из которых отвечает за отдельную бизнес-функцию.

Например:

Backend

├── Auth Service       → авторизация

├── Catalog Service    → товары

├── Order Service      → заказы

├── Payment Service    → платежи

└── Notification       → уведомления

Каждый сервис обычно:

- имеет свою бизнес-логику
- может иметь собственную базу данных
- может независимо разворачиваться и масштабироваться
- взаимодействует с другими сервисами через API, очереди или события

## Архитектурные границы

Здесь важно понимать, что все эти инструменты решают **одну общую задачу**: не дать модулям начать напрямую зависеть друг от друга и превратить модульный монолит обратно в хаотичный монолит.

Например, хотим установить правило:

catalog → shared       ✅

orders  → shared       ✅

catalog → orders       ❌

orders  → catalog      ❌

app → catalog          ✅

app → orders           ✅

Теперь разберём каждый механизм.

---

**1. ESLint rules**

**ESLint** можно использовать не только для проверки стиля кода. С его помощью можно ограничивать **импорты между модулями**.

Например, есть:

src/

├── app/

├── modules/

│   ├── catalog/

│   ├── orders/

│   └── payments/

└── shared/

Можно установить правило:

modules/catalog

    ↓

shared

modules/orders

    ↓

shared

но запретить:

catalog → orders

**Пример**

Допустим, разработчик пишет:

// catalog/ProductCard.tsx

import { Order } from '@/modules/orders';

ESLint может сказать:

Import from "modules/orders" is not allowed inside "modules/catalog"

То есть ошибка обнаруживается **еще до запуска приложения**.

**Как это реализуют?**

Обычно используют правила вроде no-restricted-imports или специализированные плагины для контроля архитектуры.

Например, концептуально:

rules: {

  'no-restricted-imports': [

    'error',

    {

      patterns: [

        '@/modules/orders/**'

      ]

    }

  ]

}

Это достаточно грубый пример. В реальном проекте правила обычно строят более системно.

**Что хорошо контролирует ESLint?**

Например:

shared → modules       ❌

catalog → orders       ❌

orders → payments      ❌

app → modules          ✅

modules → shared       ✅

**Плюс**

Ошибка появляется прямо в IDE и CI.

**Минус**

Если архитектура большая, вручную поддерживать десятки правил становится неудобно.

Поэтому для сложных проектов используют более специализированные механизмы.

---

**2. TypeScript Path Aliases**

Path aliases сами по себе **не являются полноценным инструментом контроля архитектуры**.

Они в первую очередь делают импорты понятнее.

Без alias:

import { Button } from '../../../shared/ui/Button';

С alias:

import { Button } from '@/shared/ui/Button';

Настраивается это через tsconfig.json:

{

  "compilerOptions": {

    "baseUrl": ".",

    "paths": {

      "@/*": ["src/*"]

    }

  }

}

Теперь:

import { Button } from '@/shared/ui/Button';

вместо:

import { Button } from '../../../../shared/ui/Button';

---

**Но aliases можно использовать для архитектурных границ**

Например:

{

  "paths": {

    "@app/*": ["src/app/*"],

    "@catalog/*": ["src/modules/catalog/*"],

    "@orders/*": ["src/modules/orders/*"],

    "@shared/*": ["src/shared/*"]

  }

}

Тогда структура становится очевиднее:

import { ProductCard } from '@catalog/ui';

import { Button } from '@shared/ui';

Вместо:

import { ProductCard } from '../../../modules/catalog/ui';

**Но есть важный момент**

Сам TypeScript не скажет:

catalog → orders ❌

если alias существует.

Он просто позволит написать:

import { Order } from '@orders/entities';

Поэтому aliases нужно комбинировать с ESLint или другими архитектурными правилами.

То есть:

Path aliases

      ↓

делают границы явными

ESLint / dependency rules

      ↓

запрещают нарушать эти границы

---

**3. Dependency rules**

Под **dependency rules** обычно понимают правила, которые определяют:

Какие модули имеют право зависеть друг от друга.

Это уже непосредственно архитектурный уровень.

Допустим, у нас есть:

app

catalog

orders

payments

shared

Можно определить граф зависимостей:

              app

          ↙    ↓    ↘

    catalog  orders  payments

       ↓       ↓        ↓

              shared

То есть:

app → catalog       ✅

app → orders        ✅

app → payments      ✅

catalog → shared    ✅

orders → shared     ✅

payments → shared   ✅

catalog → orders    ❌

orders → payments   ❌

payments → catalog  ❌

Получается **dependency graph**.

**Зачем это нужно?**

Представим:

catalog → orders → payments → users → catalog

Получился цикл:

catalog

   ↓

orders

   ↓

payments

   ↓

users

   ↓

catalog

Теперь изменение одного модуля потенциально затрагивает всю цепочку.

Архитектурные правила стараются не допускать таких зависимостей.

**Более реалистичный пример**

Допустим, orders хочет получить данные пользователя.

Плохой вариант:

import { UserService } from '@/modules/profile/internal/UserService';

orders полез напрямую во внутреннюю реализацию profile.

Лучше:

import { getUser } from '@/modules/profile/api';

То есть модуль предоставляет **публичный API**, а внутренности остаются скрыты.

Это уже принцип:

**Зависеть нужно от публичного контракта модуля, а не от его внутренней реализации.**

---

**4. Nx**

[Nx](https://nx.dev/?utm_source=chatgpt.com) - инструмент для управления большими monorepo.

Он умеет работать с:

- приложениями;
- библиотеками;
- зависимостями;
- задачами;
- CI;
- dependency graph;
- архитектурными ограничениями.

Например:

apps/

├── web/

└── admin/

libs/

├── catalog/

├── orders/

├── payments/

└── shared/

Nx строит граф:

web

 ├── catalog

 ├── orders

 └── shared

admin

 ├── orders

 └── shared

И может определить:

catalog → orders

как запрещенную зависимость.

**Nx tags**

Один из удобных механизмов - **tags**.

Например:

catalog → tag: scope:catalog

orders  → tag: scope:orders

shared  → tag: scope:shared

Можно определить правила:

scope:catalog → scope:shared

scope:orders  → scope:shared

Но:

scope:catalog → scope:orders ❌

Nx проверит dependency graph и выдаст ошибку.

**Еще одна важная возможность Nx**

Nx умеет понимать, какие проекты были затронуты изменением.

Например:

Изменили packages/shared/ui

             ↓

       Nx анализирует graph

             ↓

    catalog ─── affected

    orders  ─── affected

    profile ─── не affected

Тогда в CI не обязательно пересобирать весь monorepo.

---

**5. Turborepo**

[Turborepo](https://turborepo.com/?utm_source=chatgpt.com) - инструмент для управления задачами в monorepo.

Он хорошо работает с:

apps/

packages/

Например:

apps/

├── web/

└── admin/

packages/

├── ui/

├── eslint-config/

└── tsconfig/

Главная задача Turborepo - эффективно выполнять:

build

test

lint

typecheck

и учитывать зависимости между пакетами.

Например:

web

 ↓

ui

 ↓

utils

Если изменился utils, Turborepo понимает, какие задачи связаны с этим изменением.

**Важный момент**

**Turborepo не является полноценным архитектурным контроллером.**

**Turborepo** в первую очередь управляет задачами monorepo, кешированием и CI, а не архитектурными границами.

То есть его основная задача:

monorepo

   ↓

task orchestration

   ↓

build / test / lint / cache

А не:

catalog → orders ❌

Для архитектурных границ обычно используют ESLint, dependency constraints или другие инструменты.

Поэтому часто получается комбинация:

Turborepo

    ↓

управляет monorepo и CI

ESLint

    ↓

контролирует импорты

TypeScript

    ↓

контролирует типы и aliases

---

**6. Архитектурные линтеры**

Это инструменты, специально предназначенные для анализа **структуры и зависимостей проекта**.

Обычный ESLint в первую очередь анализирует отдельные файлы и код.

Архитектурный линтер смотрит шире:

Какие модули существуют?

Какие зависимости между ними?

Есть ли запрещенные зависимости?

Есть ли циклы?

Нарушается ли установленная архитектура?

Например, для JavaScript/TypeScript можно использовать **dependency-cruiser**.

Он может анализировать:

src/modules/catalog

src/modules/orders

src/modules/payments

src/shared

и строить dependency graph.

Можно задать:

catalog → shared       ✅

orders → shared        ✅

payments → shared      ✅

catalog → orders       ❌

orders → payments      ❌

Если разработчик нарушил правило, CI может завершиться ошибкой.

---

**Как всё это работает вместе**

На практике эти инструменты не обязательно конкурируют. Они решают разные задачи.

Например:

                    Frontend

                       │

              ┌────────┴────────┐

              ↓                 ↓

         TypeScript           ESLint

              │                 │

       типы и aliases     правила импортов

              │                 │

              └────────┬────────┘

                       ↓

              Архитектурные rules

                       │

                       ↓

                Dependency graph

                       │

              ┌────────┴────────┐

              ↓                 ↓

             Nx             Turborepo

              │                 │

       graph + boundaries   tasks + cache

---

**Пример реального проекта**

Допустим, у нас:

src/

├── app/

├── modules/

│   ├── catalog/

│   ├── orders/

│   └── payments/

└── shared/

Мы хотим получить такие правила:

app

 ├── catalog

 ├── orders

 └── payments

catalog ──→ shared

orders  ──→ shared

payments ─→ shared

И запретить:

catalog → orders       ❌

orders → payments      ❌

payments → catalog     ❌

shared → modules       ❌

Тогда можно использовать:

**TypeScript**

Для понятных импортов:

import { Button } from '@shared/ui';

import { Product } from '@catalog/entities';

**ESLint**

Для запрета:

import { Order } from '@orders/...';

внутри catalog.

**Dependency rules**

Для описания допустимых зависимостей:

catalog → shared

orders → shared

payments → shared

**Nx**

Если проект является Nx monorepo:

apps/

libs/

можно использовать tags и dependency graph для контроля границ.

**Turborepo**

Если используется Turborepo:

apps/

packages/

он помогает управлять:

build

test

lint

typecheck

и оптимизировать CI.

**Архитектурный линтер**

Дополнительно анализирует весь граф зависимостей и ищет:

циклы

запрещенные зависимости

неправильное направление зависимостей

---

**Главное, что стоит запомнить**

**Path aliases** помогают удобно обозначить границы:

@catalog/*

@orders/*

@shared/*

**ESLint** может запретить конкретные импорты:

catalog → orders ❌

**Dependency rules** описывают допустимое направление зависимостей:

modules → shared

**Nx** дает dependency graph и более развитые механизмы архитектурных ограничений в monorepo.

**Turborepo** в первую очередь управляет задачами monorepo, кешированием и CI, а не архитектурными границами.

**Архитектурные линтеры** анализируют структуру зависимостей и помогают обнаруживать циклы и нарушения архитектуры.

В результате архитектура перестает быть просто договоренностью команды:

"Ребята, пожалуйста, не импортируйте orders в catalog"

и превращается в **автоматически проверяемое правило**:

catalog → orders

❌ ESLint

❌ Architecture rule

❌ CI

Pull Request не проходит

Именно это особенно важно в большом проекте: **архитектурные границы должны быть не только описаны, но и технически защищены.**
