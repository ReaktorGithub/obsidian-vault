MCP (Model Context Protocol) - открытый протокол, который позволяет ИИ-моделям взаимодействовать с внешними инструментами, сервисами и данными по единому стандарту.

Если RAG помогает модели находить информацию, то MCP позволяет ей не только получать данные, но и выполнять действия: читать файлы, обращаться к API, работать с базой данных, создавать задачи и взаимодействовать с другими системами.

Например, ИИ-агент в Cursor может через MCP получить список задач из Jira, прочитать документацию из Confluence и использовать эти данные при разработке приложения.

## 1. Зачем нужен MCP

Без MCP для каждого ИИ-приложения часто приходится отдельно реализовывать интеграции с внешними сервисами.

MCP стандартизирует взаимодействие: сервис реализует MCP-сервер, а ИИ-клиент умеет подключаться к MCP-серверам и использовать предоставленные ими возможности.

LLM / ИИ-модель

Решает, какие данные получить или какое действие выполнить

MCP-клиент

Обменивается сообщениями с MCP-серверами

База данных

Файлы

Внешние API

Главная идея: MCP отделяет логику ИИ-клиента от конкретных интеграций. Один MCP-сервер может использоваться разными совместимыми клиентами.

## 2. Основные компоненты MCP

### Host

Приложение, внутри которого работает ИИ и организуется взаимодействие с MCP.

Примеры: Cursor, Claude Desktop и другие приложения с поддержкой MCP.

Host управляет подключениями, контекстом и взаимодействием модели с инструментами.

### Client

Компонент внутри Host, который устанавливает соединение с конкретным MCP-сервером и обменивается с ним сообщениями по протоколу.

Обычно для каждого MCP-сервера создаётся отдельный клиент.

### Server

Программа, которая предоставляет инструменты и данные через MCP.

Например, MCP-сервер для GitHub может предоставлять инструменты просмотра pull request, поиска репозиториев и создания issues.

Сервер может работать локально или удалённо.

## 3. Три основных примитива MCP

MCP-сервер может предоставлять три основных типа возможностей: Tools, Resources и Prompts.

Tools (инструменты)

Функции, которые ИИ может вызвать для получения данных или выполнения действий.

Примеры: создать задачу в Jira, выполнить SQL-запрос, отправить сообщение, прочитать список заказов через API.

Управление вызовом: модель обычно выбирает инструмент и аргументы, а клиент выполняет вызов через MCP.

Resources (ресурсы)

Данные, которые MCP-сервер предоставляет клиенту для использования в контексте модели.

Примеры: документация проекта, схема базы данных, содержимое файла, сведения о продукте.

Ресурсы обычно предназначены для чтения; приложение решает, когда получать и передавать их модели.

Prompts (шаблоны промптов)

Готовые шаблоны инструкций для типовых задач.

Примеры: провести code review, проверить безопасность кода, составить описание pull request.

Шаблоны помогают стандартизировать работу модели и могут принимать аргументы.

Запомнить просто:

- Tools - выполнить действие.
    
- Resources - предоставить данные.
    
- Prompts - предоставить шаблон инструкции.
    

## 4. Как работает MCP на практике

Представим, что ты работаешь в Cursor и просишь:

> Найди последние ошибки в Sentry, определи, связаны ли они с последними изменениями в коде, и предложи исправление.

Процесс выглядит так:

1. Пользователь отправляет запрос. Cursor передаёт его LLM.
    
2. Модель выбирает инструменты. Например, поиск ошибок в Sentry и просмотр коммитов в GitHub.
    
3. MCP-клиент вызывает MCP-сервер. Он передаёт название инструмента и аргументы в соответствии с его схемой.
    
4. MCP-сервер выполняет операцию. Например, обращается к Sentry API и возвращает список ошибок.
    
5. Результат возвращается модели. Она анализирует ошибки и при необходимости запрашивает дополнительные данные через другие инструменты.
    
6. Модель формирует ответ. Она предлагает исправление или, если разрешено и поддерживается окружением, выполняет изменения в коде.
    

Важно: MCP не является самой ИИ-моделью и не заставляет её автоматически выполнять действия. Он задаёт стандарт взаимодействия с внешними возможностями.

## 5. Как устроен протокол технически

MCP использует JSON-RPC 2.0 для обмена сообщениями. Это формат удалённого вызова процедур: клиент отправляет запрос с методом и параметрами, сервер возвращает результат или ошибку.

Например, условный MCP-сервер предоставляет инструмент `get_user`:

```
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_user",
    "arguments": {
      "userId": 42
    }
  }
}
```

Здесь:

- `method` - операция протокола, в данном случае вызов инструмента.
    
- `name` - название инструмента на сервере.
    
- `arguments` - аргументы функции.
    
- `id` - идентификатор запроса, позволяющий сопоставить ответ с запросом.
    

Сервер выполняет операцию и возвращает результат в формате JSON-RPC.

### Транспорт

Транспорт определяет, как сообщения передаются между клиентом и сервером.

|Транспорт|Применение|
|---|---|
|`stdio`|Локальный MCP-сервер запускается как отдельный процесс; клиент обменивается с ним данными через стандартные потоки ввода и вывода.|
|`Streamable HTTP`|Клиент взаимодействует с удалённым MCP-сервером через HTTP; поддерживается потоковая передача ответов.|

Это разные способы доставки сообщений, а не разные типы MCP-серверов.

## 6. MCP и REST API - в чём разница?

REST API позволяет приложениям взаимодействовать между собой через HTTP. MCP стандартизирует предоставление инструментов и контекста именно для ИИ-клиентов.

|REST API|MCP|
|---|---|
|Разработчик обычно заранее определяет, какие эндпоинты вызывать|Клиент может обнаружить инструменты через протокол|
|API определяет URL, HTTP-методы и формат данных|Сервер описывает инструменты, аргументы и возможности|
|Приложение самостоятельно реализует интеграцию|Совместимые ИИ-клиенты могут использовать общий MCP-интерфейс|
|Не предполагает единого стандарта инструментов для LLM|Спроектирован для обмена контекстом и вызова инструментов ИИ|

При этом MCP-сервер вполне может использовать REST API внутри своей реализации. Например, MCP-инструмент `create_issue` принимает аргументы от модели и вызывает REST API GitHub.

## 7. MCP и RAG - в чём разница?

Это разные, но совместимые подходы.

|RAG|MCP|
|---|---|
|Находит релевантную информацию для ответа|Предоставляет стандартный доступ к данным и инструментам|
|Часто использует embeddings и векторную базу|Не требует векторной базы данных|
|Передаёт найденные фрагменты в контекст LLM|Может предоставить поиск, чтение данных или выполнение действий|
|Обычно применяется для поиска по документам|Применяется для интеграций с сервисами и данными|

Например, MCP-сервер может предоставлять инструмент поиска по корпоративной документации, внутри которого реализован RAG. MCP обеспечивает интерфейс вызова, а RAG - поиск релевантных фрагментов.

## 8. MCP и обычный function calling

Function calling - механизм, с помощью которого модель предлагает вызвать функцию с определёнными аргументами.

MCP - протокол, по которому приложения могут обнаруживать и вызывать инструменты, а также получать ресурсы и шаблоны промптов.

Они не конкурируют напрямую. MCP-сервер предоставляет инструменты, клиент передаёт их описание модели, а модель может выбирать их с помощью function calling. Клиент обрабатывает этот выбор и вызывает сервер.

## 9. Безопасность MCP

MCP-сервер может иметь доступ к файлам, базам данных и внешним сервисам, поэтому важно:

- Ограничивать права доступа только необходимыми операциями и данными.
    
- Проверять и валидировать аргументы каждого инструмента.
    
- Использовать надёжную аутентификацию и авторизацию для удалённых серверов.
    
- Запрашивать подтверждение пользователя перед опасными действиями, например удалением данных или отправкой сообщений.
    
- Не доверять автоматически содержимому файлов и ответам внешних сервисов: там могут находиться вредоносные инструкции.
    
- Проверять происхождение MCP-серверов и не подключать неизвестные серверы с широкими правами.
    

MCP не гарантирует безопасность сам по себе: она зависит от реализации сервера, клиентского приложения и настроенных разрешений.

## 10. Где MCP применяется frontend-разработчику

В твоём стеке React, TypeScript и Node.js MCP может быть полезен в нескольких сценариях:

- Cursor: доступ ИИ-агента к документации, GitHub, Sentry, файловой системе и другим сервисам.
    
- Внутренние инструменты: подключение ИИ-ассистента к API компании, базе знаний и бизнес-операциям.
    
- Разработка собственного MCP-сервера на Node.js: создание инструментов для чтения данных, работы с API или запуска разрешённых операций.
    
- Автоматизация разработки: получение сведений о задачах, поиск ошибок, подготовка отчётов и анализ изменений в коде.
    

Итого для собеседования: MCP - открытый протокол стандартизированного взаимодействия ИИ-приложений с внешними инструментами и источниками данных. Его основные компоненты - Host, Client и Server, а основные примитивы - Tools, Resources и Prompts.
