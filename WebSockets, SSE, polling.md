### WebSockets

Постоянное **двустороннее соединение** между клиентом и сервером. После установки соединения обе стороны могут отправлять данные в любой момент.

- Real-time чаты
- онлайн-игры
- биржевые котировки
- совместное редактирование

Client ⇄ Server

---

### Socket.IO

Библиотека для работы с real-time коммуникацией поверх WebSocket и других транспортов.

Даёт готовые механизмы:

- автоматический reconnect
- rooms
- events
- acknowledgements
- fallback на другие транспорты

Важно: **Socket.IO ≠ WebSocket**. Это более высокоуровневое решение.

---

### SSE (Server-Sent Events)

Постоянное **однонаправленное соединение**: сервер может отправлять события клиенту, но клиент не отправляет данные через это же соединение.

Работает поверх обычного HTTP.

Client ──────→ Server

       ←────── Server

Используется для:

- уведомлений
- прогресса операций
- стриминга данных
- AI-ответов

В браузере есть готовый API:

const source = new EventSource('/events')

  

source.onmessage = event => {

  console.log(event.data)

}

### Polling

Клиент **периодически делает HTTP-запросы**, чтобы узнать, появились ли новые данные.

Client → Server

Client → Server

Client → Server

...

Например:

setInterval(() => {

  fetch('/notifications')

}, 5000)

Просто реализуется, но создаёт лишние запросы и задержку между появлением данных и их получением.

---

### Главное различие

|Технология|Направление|Соединение|Real-time|
|---|---|---|---|
|**Polling**|Client → Server|отдельные HTTP-запросы|❌|
|**SSE**|Server → Client|постоянное|✅|
|**WebSocket**|Client ⇄ Server|постоянное|✅|
|**Socket.IO**|Client ⇄ Server|абстракция над transport|✅|

**Запомнить:**  
**Polling** — «спроси ещё раз через N секунд».  
**SSE** — «сервер сам присылает обновления».  
**WebSocket** — «клиент и сервер постоянно связаны и могут общаться в обе стороны».  
**Socket.IO** — удобная библиотека для такой коммуникации.

### Short Polling

Клиент **через определённый интервал** отправляет новый HTTP-запрос.

Client → Server

         ↓

       response

         ↓

      ждём 5 сек

         ↓

Client → Server

         ↓

       response

setInterval(() => {

  fetch('/messages')

}, 5000)

**Минус:** много лишних запросов и задержка до следующего polling.

---

### Long Polling

Клиент отправляет запрос, а сервер **не отвечает сразу**, а держит соединение открытым, пока не появятся новые данные или не наступит timeout.

Client → Server

           │

           │ ждём данные

           │

           ↓

        response

           ↓

Client → Server

           │

           │ ждём снова

Например:

Client → GET /messages

             ↓

          Server ждёт

             ↓

       появилось сообщение

             ↓

          Response

             ↓

Client → GET /messages

**Плюс:** меньше пустых запросов и быстрее реакция.

**Минус:** серверу приходится держать много открытых HTTP-соединений.

### Главное различие

**Short polling:**

> «Проверяй каждые 5 секунд».

**Long polling:**

> «Держи мой запрос и ответь, когда появятся данные».

По степени realtime обычно:

**Short Polling → Long Polling → SSE → WebSocket**.
