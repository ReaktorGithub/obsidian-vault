LLM

Ещё одним интересным направлением был чат с LLM-моделями. Нужно было сделать интерфейс, в котором пользователь мог выбирать доступные модели, вести диалог и получать асинхронные ответы. Я реализовывал сам клиентский сценарий: динамическую загрузку моделей через API, управление состоянием диалога и обработку ответов. В итоге это был интерактивный сценарий, где важно корректно работать с асинхронностью и состояниями загрузки.

Тарифы, формы

Из более прикладных задач я также занимался бизнес-логикой тарифов и пользовательских настроек. Например, были сложные формы на React Hook Form, данные которых нужно было сохранять и синхронизировать с backend через GraphQL и Apollo Client.

Виртуализация

Отдельно я занимался производительностью. В проекте были большие таблицы с данными рекламных кампаний, поэтому я реализовал виртуализацию через react-virtualized. Это позволило не пытаться отрисовывать на странице сразу весь объём данных и сделало работу с большими наборами данных значительно стабильнее.

### Про Node js

На AdSensor был отдельный Node.js BFF для работы фронтенда с несколькими backend-сервисами. Я дорабатывал API для страницы аналитики рекламных кампаний: Node.js принимал параметры фильтрации и пагинации от React, запрашивал данные из нескольких сервисов, объединял их и отдавал фронтенду уже в удобном формате. Это позволило не тащить сложную бизнес-логику и несколько запросов на клиент, а также уменьшило количество сетевых запросов со стороны SPA.

Для такой легенды можно сказать, что использовал:

- Node.js + Express - сам BFF и REST API
- TypeScript - типизация DTO и ответов
- Axios - запросы к backend-сервисам
- Redis - кэширование часто запрашиваемой аналитики
- PostgreSQL - если BFF должен был обращаться к своей небольшой служебной БД
- JWT - проброс и проверка авторизации
- Docker - запуск BFF в контейнере

### Про CI CD

Участвовал в поддержке CI/CD-процессов фронтенда. Работал с пайплайнами, которые запускали линтер, проверку TypeScript, тесты и production-сборку при создании Pull Request. Также участвовал в настройке автоматического деплоя на тестовое окружение и проверке сборки перед выпуском в production.

Что ты можешь рассказать подробнее, если интервьюер начнёт задавать вопросы:

- Инструменты: GitLab CI/CD или GitHub Actions - выбери тот, с которым действительно работал или который готов уверенно объяснить.
    
- Проверки: ESLint, TypeScript (`tsc --noEmit`), unit-тесты, production-сборка.
    
- Процесс: разработчик создаёт Pull Request, пайплайн запускает проверки, после успешного прохождения изменения можно слить в основную ветку.
    
- Деплой: после слияния изменений собирается приложение, артефакты передаются на сервер или в хранилище, затем обновляется тестовое либо production-окружение.
    

Если спросят, что именно ты сделал, можно привести пример: добавил проверку TypeScript в пайплайн, чтобы ошибки типов обнаруживались до слияния кода, а не после деплоя.

Важно: это заготовка для подготовки, а не подтверждение твоего реального опыта. Не утверждай, что настраивал конкретный инструмент или production-деплой, если этого не было. Лучше опираться на ту часть CI/CD, которую сможешь технически объяснить на собеседовании.
