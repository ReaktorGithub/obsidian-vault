### Вертикальное и горизонтальное масштабирование

Вертикальное масштабирование — наращивание мощности одной машины.

Горизонтальное масштабирование — противоположный ход. Вместо того чтобы увеличивать показатели одной машины, мы ставим рядом вторую, потом третью.

В Kubernetes возможность масштабировать сервис заложена изначально: в YAML-файле есть параметр `replicas`. Пишем `replicas: 2` — получаем два экземпляра сервиса. Работает это одинаково и для бэкенд-сервиса, и для фронта. И между клиентом и репликами обязан появиться балансировщик.

### Fallback и graceful degradation

**fallback** — запасной путь. Классический случай — платёжный шлюз: если основная платёжка не отвечает, нужна запасная, которая в случае чего обработает платежи.

**graceful degradation**, плавная деградация. Если сервис не работает, отключение должно быть плавным: пользователь не должен сталкиваться с непредвиденным поведением, когда система ведёт себя непонятно и непредсказуемо. Реализуется это приземлённо — мы заранее ставим определённые условия: если запрос не доходит, идём туда-то и туда-то.

# Партиционирование: горизонтальное и вертикальное

**Партиционирование и шардирование данных** — это методы разделения базы данных на более мелкие части для повышения производительности как записи, так и чтения.

**Партиционирование** — это когда мы чисто логически разбиваем пользователей по каким-то правилам на определённые сегменты базы.

**Шардирование** — это уже прямо отдельные шарды, отдельные базы, куда мы закидываем наши изменения, разнесённые по разным инстансам. (_«одна база у нас будет нагружаться сильнее, чем несколько»)

**Горизонтальное партиционирование** — это когда данные делятся по строкам, по записям, на основе значения определённых полей. Каждая партиция содержит подмножество строк одной таблицы; меняется только то, какие именно записи попадают в конкретную часть.

**Вертикальное партиционирование** — это когда данные делятся по столбцам. Каждая партиция содержит только определённые столбцы таблицы. Применимо это тогда, когда разные группы данных используются в разных контекстах.

|                         | Горизонтальное                                           | Вертикальное                                                           |
| ----------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------- |
| Что делим               | строки, записи                                           | столбцы                                                                |
| Что содержит партиция   | подмножество строк одной таблицы                         | только определённые столбцы таблицы                                    |
| Критерий деления        | значение определённых полей (регион, диапазон id)        | контекст использования группы данных                                   |
| Примеры                 | Европа / Америка; id 1–1000 и 1001–2000                  | common data / passport data; редкие поля профиля; контакты / настройки |
| Насколько формализовано | есть определённые правила (range-based и другие подходы) | условно, в каждом случае по-своему                                     |
Шардирование — это разновидность горизонтального партиционирования, применяемая в распределённых системах, то есть там, где есть разные инстансы системы.

Основное отличие формулируется одной фразой: **данные распределяются по разным физическим узлам** — серверам, базам данных и так далее.

|Подход|Как определяется шард|Сильная сторона|Слабое место|
|---|---|---|---|
|Range-based|По диапазону значений ключа (id, возраст, номер)|Самое сбалансированное распределение|Непонятно, как выбирать границы диапазонов|
|Hash-based|Хэш-функция от уникального поля (например, email)|Решение принимает сама функция, руками ничего не прописываем|Равномерность не гарантирована: в одном шарде 500 записей, в другом 4|
|Direction-based|Явный справочник «ключ → номер шарда»|Полный контроль: конкретная запись лежит там, где указано|Равномерность приходится обеспечивать самим|
### Географическое шардирование

Отдельный вид — географическое шардирование. Здесь данные пользователей распределяются **по физическим местоположениям**

### Что такое перебалансировка

Данные распределены между несколькими базами. Один из шардов перестал работать — данные, которые на нём лежали, никуда не делись, но получить их через этот узел невозможно. Значит, оставшиеся шарды должны взять его нагрузку на себя, то есть заново поделить между собой диапазон ключей. Перераспределение данных между оставшимися узлами и есть **перебалансировка**.

### Итого:

|Механизм|Что делает|Где живут данные|
|---|---|---|
|Репликация|Копируем данные ради их извлечения|Полные копии одного и того же набора данных|
|Шардирование|Разбиваем данные на разные инстансы базы|Инстансы могут физически находиться где угодно|
|Партиционирование|Разбиваем данные на части|В пределах одного инстанса базы данных|
### CAP-теорема

CAP-теорема: **распределённая система может соответствовать только двум правилам из трёх**.

**1. Согласованность.** Все узлы системы видят одни и те же данные. Пользователь приходит в систему и не должен сталкиваться с тем, что он только что зарегистрировался, а ему приходит ошибка «такого пользователя нет». Такого быть не может — везде одни и те же данные.

**2. Доступность.** Каждый запрос к системе получает ответ, даже если некоторые узлы недоступны. Короткая формулировка: _«всегда получим ответ»_.

**3. Устойчивость к разделению.** Система продолжает работать, даже если происходит разъединение сети, то есть узлы перестали видеть друг друга.
