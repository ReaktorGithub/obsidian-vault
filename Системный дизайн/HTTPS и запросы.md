
**HTTPS = HTTP + SSL-сертификат + TLS-протокол**

**Симметричное шифрование** — когда ключ один: им и шифруем, и расшифровываем.

**Асимметричное шифрование** устроено иначе: ключей два, и они не взаимозаменяемы. Один закрывает данные, другой — открывает.

### Как это работает в HTTPS целиком

Собираем всё вместе:

- **Приватный ключ находится на сервере.**
- **Открытым ключом шифруется информация** на стороне клиента.
- Каждый раз, когда мы что-то отправляем — заходим на ресурс, что-то там делаем, шлём запросы, — данные шифруются открытым ключом.
- Данные идут по сети в зашифрованном виде: _«и всё, никто не видит»_ — перехватчик на модеме или на шлюзе-прокладке получает нечитаемый поток, а не ваш логин в банк.
- Данные доходят до сервера, сервер их расшифровывает — и коммуникация продолжается в обычном режиме.

## Из чего состоит любой запрос

Запрос — набор определённых полей, которые заполняются каждый раз. Стандартная конфигурация выглядит так:

- **url** — адрес ресурса, например `https://google.com`;
- **method** — метод запроса, скажем `POST` или `GET`;
- **headers** — заголовки;
- **body** — тело запроса.

Это тот минимальный скелет, который стоит держать в голове и воспроизводить, когда просят расписать запросы в проектируемой системе.

| Метод         | Назначение                                                   |
| ------------- | ------------------------------------------------------------ |
| GET           | Получение одной или нескольких записей                       |
| POST          | Внесение данных                                              |
| PUT           | Обновление всей записи                                       |
| PATCH         | Обновление части записи                                      |
| DELETE        | Удаление                                                     |
| HEAD          | Как GET, но без тела ответа — только заголовки ресурса       |
| OPTIONS       | Возвращает список доступных методов для ресурса              |
| TRACE         | Возвращает запрос клиента в ответе сервера (диагностика)     |
| CONNECT       | Устанавливает туннель, например для работы HTTP через прокси |
| LINK / UNLINK | Связывает ресурс с другим ресурсом либо убирает связь        |
Запрос — это url, method, headers и body. Тело есть у всех методов, кроме `GET`. Query-параметры — часть URL после знака вопроса, а не отдельная секция. Cookie едут в заголовке и при авторизации устанавливаются сами, без участия фронтенда. Первые пять методов образуют обычный REST-набор, остальные — специфичные, и все они — просто значение поля `method` в том самом скелете запроса, с которого мы начали.

### REST-архитектура

Про REST чаще всего говорят в связке со словом «архитектура». REST-архитектура строится на том, что существуют определённые правила и им нужно следовать. Правила при этом не жёсткие: _«правила эти не строгие, но соблюдать надо»_.

Правила REST:

**1. Разделение на клиент-сервер.**

**2. Без хранения состояния.**

**3. Кэширование ресурсов.**

**4. Единообразие интерфейсов.**

**5. Многослойность.** Система многослойная, и каждый слой не знает о других. Не должно быть такого, чтобы один слой каким-то образом влиял на другой. Разные слои, разные уровни абстракции, разные сервисы — и все они находятся друг относительно друга в неведении.

**6. Предоставление кода по апплетам (code on demand).** Самый спорный пункт списка. Идея в том, что есть запрос на код: этот код отправляется — и он исполняется.

### RESTful

Если система соответствует всем этим правилам, REST превращается в RESTful — то есть в полноценную REST-архитектуру. Само слово здесь работает как оценка: насколько реализация действительно следует принципам.

### SOAP: тот же обмен, но в XML

XML — многословный формат: в нём большое количество ненужных слов, которые полезной информации не несут, но исправно едут по сети. Передача нагружает канал и идёт долго. Плюс сама модель работы получается тяжёлой: _«это сложное, это старое, поддерживать это неудобно, и зачем нам это использовать»_.

### GraphQL: одна ручка и ответ, который клиент собирает сам

GraphQL — это всё поверх HTTP, никакого отдельного транспорта здесь нет. Суть подхода в другом: вместо набора ручек под каждый сценарий есть одна определённая ручка. Клиент делает запрос на неё и получает данные.

Недостатки GraphQL:

Чтобы сопоставить запрос — query или мутацию — с реальными данными, сервер вынужден делать определённые подзапросы к базе.

**страдает кэширование**. Кэшировать можно то, что предсказуемо: мы заранее знаем, какой ответ отдадим на такой-то запрос. В GraphQL ответы каждый раз разные, потому что каждый раз клиент просит свой набор полей. Раз предугадать, что мы будем отдавать, не получается, — то и закэшировать это мы не сможем.

_«То, что GraphQL делает хорошо на фронте, он немного ухудшает на бэке»_ — это и есть короткая формулировка всего компромисса.

### gRPC: удалённый вызов процедур и бинарный формат

RPC — это удалённый вызов процедур. Буква «g» впереди объясняется просто: _«а почему g? Потому что всё на гугле»_.

Как это устроено. Есть protobuf-файл — описание контракта. Он лежит и на клиенте, и на сервере и описывает, как стороны будут коммуницировать между собой: какие процедуры существуют и как. Дальше происходит подключение — тоже по HTTP, по определённой ручке. Соединение установлено, и после этого мы начинаем **удалённо вызывать процедуры**: клиент вызывает процедуру у себя, через protobuf-описание запрос доходит до сервера, там процедура выполняется, и клиент получает ответ.

gRPC обычно используется в коммуникации между микросервисами — тем самым эта коммуникация становится быстрой.

### WebSocket: пробитый канал вместо череды запросов

Между двумя сторонами получается просто прямая линия. Мы соединились — и дальше **в режиме реального времени** клиент и сервер опрашивают друг друга и передают данные.

### Идемпотентность запросов

Запросы должны быть **идемпотентными**. Идемпотентность означает, что операция выполняется один раз, а все последующие одинаковые вызовы не приводят ни к каким дополнительным эффектам.

### Overfetching и underfetching

**overfetching** — когда мы отдаём слишком много данных, **underfetching** — когда слишком мало.
