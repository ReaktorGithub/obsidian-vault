**Rolling release** — это стратегия, при которой обновление программы или системы происходит постепенно, а не сразу целиком. Обновляться может одна часть инфраструктуры или несколько частей одновременно — и так до тех пор, пока все компоненты не окажутся на новой версии.

**blue-green**. Это метод, при котором есть две одинаковые версии системы:

- **blue (синяя)** — текущая рабочая система, та, что прямо сейчас обслуживает пользователей;
- **green (зелёная)** — новая версия, которую мы разворачиваем.

**Canary release** — это стратегия, при которой новая версия сразу разворачивается для небольшой группы пользователей.

### CQRS: разделение команд и запросов

**CQRS** (Command Query Responsibility Segregation) — разделение команд и запросов. На человеческий язык это переводится так: команды — на внесение данных, запросы — на получение. То есть вся работа с данными делится на две категории:

- **команды** — мутации: изменения, добавление, всё, что меняет состояние;
- **запросы** — чтение, получение данных наружу.

### Функциональное разделение

Запросы и команды выносятся в логически разные приложения — по сути, в разные сервисы: один отвечает за внесение данных, другой за их получение.

### Event sourcing: хранение и опора на события

event sourcing — событийно-ориентированная архитектура, когда мы работаем с событиями, а не только с текущим состоянием.

Три канонических примера, которые стоит держать в голове:

- **баланс** — складывается из событий депозита и вывода средств;
- **история платежей** — все входящие и исходящие операции пользователя;
- **статусы заказа** — создан, в пути, получен.

### Pub/Sub: издатель и подписчик

Есть **publisher** (издатель) и есть **subscriber** (подписчик).

Банальный пример — YouTube. Автор закинул видео, у видео стоит колокольчик. Subscriber подписан на нашего publisher, видит это сообщение и потребляет его: узнаёт, что появилось новое видео, и идёт его смотреть. Ключевая мысль в том, что **сам канал доставки не зафиксирован**. Это может реализовываться разными форматами

# Устойчивость

| Приём   | Что делает                                                | Когда применяется                                                                                  |
| ------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Retry   | Повторяет запрос, пока не будет получен ответ             | Ответ отрицательный или запрос невозможно обработать                                               |
| Backoff | Повторяет запрос через n секунд, с паузой между попытками | Там же, где retry, — чтобы повторы не были неоптимизированными (даем время ошибке, чтобы она ушла) |
Fallback (резервный вариант) - это механизм переключения на альтернативный способ выполнения операции, если основной способ недоступен или завершился ошибкой.

Пример: приложение пытается загрузить данные с основного API. Если запрос падает, оно обращается к резервному API или показывает закэшированные данные.

**graceful degradation** - _Если новая фича сломана, то нужно её отключить_

- **оркестрация** — логика сосредоточена в оркестраторе, сервисы простые и друг о друге не знают;
- **хореография / чейнинг** — логики в одном месте нет, она размазана по цепочке, каждый сервис сам решает, что дальше.
