
- **Cache miss (кэш-промах)** — мы обращаемся к кэшу, а там ничего нет. Данных в кэше не оказалось.
- **Cache hit (кэш-попадание)** — обратная ситуация: данные в кэше есть, и мы отдаём их сразу.
- **Соотношение попаданий и промахов** — кэш-хит поделить на кэш-мис, cache ratio. Точное название не принципиально, важна сама метрика: насколько часто кэш реально срабатывает.
- **Инвалидация кэша** — принудительная очистка закэшированных данных. Тем, кто работал с фронтендом, механизм знаком по тегам: React и Next дают возможность навесить на запрос тег и закэшировать по нему ответ, а потом по тому же тегу данные сбросить. Похожая история с тегами есть и во Vue.
- **Прогрев кэша** — ситуация, когда в кэше пусто и хранилище нужно заранее заполнить данными.

Внутреннее кэширование — когда сервис кэширует данные у себя внутри. Внешнее — когда за нас значения хранит отдельный источник

### Cache-aside: приложение само управляет кэшем

1. Приходит запрос — приложение сначала проверяет кэш на наличие нужных данных.
2. Данные есть — отдаём их, на этом всё.
3. Данных нет — приложение загружает их из источника данных: из базы или откуда-то ещё.
4. Полученный результат сохраняется в кэш для последующего использования: в следующий раз эти данные придут уже не из базы, а из кэша.
### Cache-through: запрос проходит через кэш (используется редко)

1. Клиент запрашивает данные — запрос попадает в кэш.
2. Если данные в кэше есть, они сразу возвращаются клиенту.
3. Если данных в кэше нет, подключается приложение: оно автоматически загружает их из источника данных, то есть из базы, и сохраняет в кэше перед возвратом клиенту.
### Cache-ahead: сначала кэш, потом база (используется редко)

Эта модель предполагает, что приложение записывает данные в кэш **до их фактического использования**.

**данные можно потерять**

| Модель        | Кто ходит в кэш                                            | Порядок работы                                      | Насколько распространена           |
| ------------- | ---------------------------------------------------------- | --------------------------------------------------- | ---------------------------------- |
| Cache-aside   | Само приложение (сервис)                                   | Промах → база → запись в кэш                        | Самая частая, вариант по умолчанию |
| Cache-through | Запрос идёт через кэш, при попадании до сервиса не доходит | Промах → сервис → база → обновление кэша            | Крайне редко                       |
| Cache-ahead   | Приложение пишет в кэш заранее                             | Кэш → синхронизация с базой (синхронно или пакетно) | Редко, специфичные случаи          |
**Вытеснение кэша** (cache eviction)

### Random — случайный выбор

Самый простой вариант: выкинуть случайную запись

### FIFO — обычная очередь

FIFO расшифровывается как _first in, first out_: кто первым пришёл, тот первым и уйдёт. Это поведение обычной **очереди**

### LIFO — стек

LIFO — это _last in, first out. Уйдёт та запись, которая попала в кэш последней

### LRU — по времени последнего обращения

LRU (_least recently used_) — вытесняется тот элемент, к которому **дольше всего не обращались**

### MRU — наоборот, самый свежий

MRU (_most recently used_) — противоположность LRU: из кэша вылетает **последний использованный** элемент

### LFU — по количеству обращений

Вытесняется самый непопулярный элемент.

### Кэш на клиенте

**Lazy loading (ленивая загрузка).** Идея простая: подгружаем в зависимости от нужды

**Code splitting (разделение кода).** Бандл режется на части, чтобы было что подгружать по требованию: без разделения кода ленивой загрузке просто нечем оперировать.

**Tree shaking.** Сборщик может убрать лишний код.

**CDN (Content Delivery Network).** Ускоряет скорость загрузки. По сути это просто копия нашего ресурса, размещённая где-то ещё

### Заголовки кэширования

**Cache-Control** управляет политикой кэширования: срок действия, видимость кэша, как именно мы кэшируем. Это ответ на вопрос _«как храним кэш»_.

**ETag** помогает определить, изменился ли ресурс, чтобы избежать передачи лишних запросов. Это ответ на вопрос _«изменился ли кэш»_.

### Service Workers

Это скрипт, работающий в фоновом режиме для браузера и предоставляющий возможность кэширования, перехвата сетевых запросов и управления ими. В первую очередь это ключевой инструмент для создания офлайн-приложений — тех, что продолжают работать даже без подключения к интернету.
