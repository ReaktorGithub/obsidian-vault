**Session Auth**

**Сессия** - паттерн реализации авторизации, при котором сервер хранит состояние сессии пользователя, а браузер передает серверу идентификатор этой сессии.

**Что происходит при авторизации**

Когда пользователь вводит логин и пароль:

1. Сервер получает логин и пароль и **проверяет пароль**. Пароли обычно хранятся в БД не в виде обычного хэша MD5/SHA-1, а с использованием специализированных алгоритмов, например **Argon2, bcrypt или scrypt**, с солью.
2. Если данные верны, сервер **создает сессию** и сохраняет ее на своей стороне. У сессии обычно есть session_id, срок действия (expires_at) и, например, идентификатор пользователя.
3. Сервер отправляет браузеру cookie:

Set-Cookie: session_id=abc123...;

  HttpOnly;

  Secure;

  SameSite=Lax;

  Max-Age=3600

4. Браузер **сам сохраняет cookie** и в дальнейшем автоматически отправляет ее с запросами к соответствующему домену.

**Основные атрибуты cookie**

- **HttpOnly** - JavaScript не может прочитать cookie через document.cookie. Это снижает риск кражи сессии через XSS.
- **Secure** - cookie отправляется только по HTTPS.
- **SameSite** - ограничивает отправку cookie в cross-site запросах и помогает защищаться от CSRF.
- **Expires / Max-Age** - определяет срок жизни cookie.

**Что происходит после F5**

После перезагрузки страницы браузеру не нужно заново авторизовываться:

1. При запросе к серверу браузер автоматически добавляет cookie:

GET /profile

Cookie: session_id=abc123...

2. Сервер получает session_id, находит соответствующую сессию и проверяет, **существует ли она и не истек ли срок ее действия**.
3. Если сессия действительна, сервер понимает, какому пользователю она принадлежит, и предоставляет доступ к защищенным ресурсам.

То есть **логин и пароль после каждой перезагрузки не передаются** - браузер использует сохраненный session_id.

**Безопасность Session ID**

Если злоумышленник получит действующий session_id, он во многих реализациях сможет **выдать себя за пользователя**, пока сессия действительна.

Поэтому хороший session_id должен:

- быть **случайным и непредсказуемым**;
- иметь достаточную длину и энтропию;
- передаваться только по HTTPS;
- быть недоступным JavaScript через HttpOnly;
- инвалидироваться при **logout**;
- иметь разумный срок жизни;
- генерироваться заново после успешной аутентификации, чтобы предотвращать **session fixation**.

Если кто-то получит session_id, то он получит доступ к сессии юзера и сможет от его имени совершать все операции.

**Logout**

·  Клиент отправляет запрос с текущей **session cookie**.

·  Сервер находит сессию и **удаляет/инвалидирует её** в session storage.

·  Сервер обычно отправляет Set-Cookie с истёкшим сроком, чтобы удалить session cookie в браузере.

·  Клиент очищает локальное auth-состояние: user, cached data, store и т.д.

·  После этого запросы без валидной сессии получают 401 Unauthorized.

# JWT

**JWT (JSON Web Token)** - формат токена, который часто используется для реализации авторизации. Сам JWT не является отдельным протоколом авторизации, а представляет собой **стандартизированный формат токена**.

## Что происходит при авторизации

Когда пользователь вводит логин и пароль:

1.      Сервер получает логин и пароль и проверяет пароль. В БД пароль должен храниться не через MD5/SHA-1, а с помощью специализированных алгоритмов, например **Argon2, bcrypt или scrypt**, с солью.

2.      Если данные верны, сервер создает:

o   **Access Token** - обычно короткоживущий JWT;

o   **Refresh Token** - долгоживущий токен для получения нового Access Token.

3.      Refresh Token сервер сохраняет или связывает с серверной записью о сессии/устройстве. Access Token обычно **не хранится на сервере**, поэтому сервер может проверить его самостоятельно.

4.      Сервер отправляет токены клиенту.

Важно: JWT и Refresh Token не обязательно должны использоваться вместе. Это распространенная архитектура, но возможны и другие варианты.

## Что происходит на фронте

После успешного логина фронтенд получает токены от сервера.

Обычно:

·        **Access Token** используется для API-запросов.

·        **Refresh Token** используется только для получения нового Access Token.

Access token сохраняется в памяти приложения, а **Refresh Token устанавливает сам браузер в куках. Это** **происходит** **благодаря** **хедеру** Set-Cookie: refresh_token=abc123; HttpOnly; Secure; SameSite=Lax

Например:

```
POST /api/v1/auth/login
```

```
{
```

```
  "email": "user@example.com",
```

```
  "password": "password"
```

```
}
```

Сервер отвечает:

```
{
```

```
  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
```

```
  "refreshToken": "..."
```

```
}
```

После этого фронтенд использует Access Token при обращении к защищенному API:

```
GET /api/v1/jwt/data
```

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

Если Access Token истек, фронтенд отправляет Refresh Token на специальный endpoint:

```
POST /api/v1/auth/refresh
```

Сервер проверяет Refresh Token и, если он действителен, выдает новый Access Token.

### Где хранить токены

Наиболее безопасный распространенный вариант для веб-приложения:

·        **Refresh Token** хранить в `HttpOnly + Secure + SameSite` cookie. JavaScript не сможет его прочитать.

·        Access Token можно хранить **в памяти приложения**. После перезагрузки страницы его придется получить через Refresh Token.

·        Хранение токенов в `localStorage` удобно, но при XSS злоумышленник может получить токен через JavaScript.

Конкретный способ зависит от архитектуры приложения и требований безопасности.

# Из чего состоит JWT

JWT обычно выглядит примерно так:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
```

```
.
```

```
eyJzdWIiOiIxMjMiLCJyb2xlIjoidXNlciIsImV4cCI6MTcyMDAwMDAwMH0
```

```
.
```

```
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

JWT состоит из трех частей, разделенных точками:

```
Header.Payload.Signature
```

### 1. Header

Содержит служебную информацию, например:

```
{
```

```
  "alg": "HS256",
```

```
  "typ": "JWT"
```

```
}
```

·        `alg` - алгоритм подписи;

·        `typ` - тип токена.

**Header не зашифрован.**

### 2. Payload

Содержит claims - данные о токене и пользователе:

```
{
```

```
  "sub": "123",
```

```
  "role": "user",
```

```
  "exp": 1720000000
```

```
}
```

Например:

·        `sub` - идентификатор пользователя;

·        `role` - роль;

·        `exp` - время истечения токена;

·        `iat` - время выпуска токена.

**Payload также не зашифрован.** Он просто закодирован в Base64URL.

Поэтому в JWT **нельзя хранить пароли, секреты и другую чувствительную информацию**.

Например, если записать:

```
{
```

```
  "password": "123456"
```

```
}
```

это не сделает пароль секретным - содержимое можно легко декодировать.

### 3. Signature

Подпись позволяет серверу проверить, что токен:

·        действительно был подписан доверенным ключом;

·        не был изменен после выпуска.

Например, для HMAC алгоритма подпись концептуально создается из:

```
HMAC(
```

```
  secret,
```

```
  base64url(header) + "." + base64url(payload)
```

```
)
```

Сервер пересчитывает подпись и сравнивает ее с той, что находится в JWT.

Поэтому серверу **не нужно обращаться к БД для проверки самого JWT**. Но БД все равно может понадобиться для проверки других вещей: существует ли пользователь, не отозван ли токен, какие у пользователя права и т.д.

### Важное отличие: JWT не шифруется

JWT обычно **подписывается, а не шифруется**.

Это означает:

**Закодировать** → изменить представление данных, но не скрыть их.  
**Зашифровать** → скрыть данные, имея возможность расшифровать их ключом.  
**Хэшировать** → получить необратимое значение фиксированной длины.  
**Подписать** → подтвердить целостность и подлинность данных с помощью криптографического ключа.

# Access Token

Access Token обычно живет недолго, например **5-15 минут**.

Если злоумышленник украдет действующий Access Token, он сможет использовать его от имени пользователя до тех пор, пока токен не истечет или не будет иным образом отозван.

После истечения срока действия Access Token фронтенд получает новый через Refresh Token.

---

# Refresh Token

Refresh Token обычно живет значительно дольше Access Token - например, несколько дней или недель.

Он используется **не для доступа к обычным API**, а для получения нового Access Token.

Refresh Token может быть:

·        **одноразовым (rotating)** - после использования сервер выдает новый Refresh Token, а старый инвалидируется;

·        многоразовым - пока не истек его срок действия или он не был отозван.

Поэтому утверждение, что Refresh Token всегда одноразовый, неверно.

При **Refresh Token Rotation** схема выглядит так:

```
Refresh Token 1
```

```
      ↓
```

```
POST /refresh
```

```
      ↓
```

```
Access Token 2 + Refresh Token 2
```

```
      ↓
```

```
Refresh Token 1 инвалидируется
```

Если злоумышленник попытается повторно использовать уже инвалидированный Refresh Token, сервер может обнаружить компрометацию сессии и отозвать всю цепочку токенов.

При этом **Refresh Token не обязательно является JWT**. Очень часто это просто длинная случайная строка, которая сама по себе не содержит полезной информации.

# Stateless

Авторизация с JWT часто называется **stateless**, потому что серверу не обязательно хранить состояние каждого Access Token.

Например, сервер может проверить:

```
JWT → подпись → exp → claims → доступ разрешен
```

без запроса в БД.

Плюс такого подхода - меньше обращений к хранилищу для проверки Access Token и проще горизонтально масштабировать API.

Но JWT **не делает систему полностью stateless автоматически**. Если Refresh Token хранится на сервере, сервер все равно хранит состояние refresh-сессий.

Также JWT не обязательно быстрее обычной session auth: проверка подписи тоже требует вычислений, а реальная производительность зависит от архитектуры и инфраструктуры.

---

# Authorization: Bearer

Для передачи Access Token обычно используется HTTP-заголовок:

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

Синтаксис:

```
Authorization: <auth-scheme> <authorization-parameters>
```

**Bearer** означает, что тот, кто предъявляет этот токен, получает доступ к ресурсу в соответствии с правами токена.

Важно: `Bearer` не является частью JWT и не означает, что токен обязательно связан с OAuth 2.0. Это HTTP authentication scheme, которая также широко используется для JWT.

**OAuth 2.0** - протокол делегированной авторизации.

Он позволяет одному приложению получить ограниченный доступ к ресурсам пользователя в другом сервисе **без передачи этому приложению пароля пользователя**.

Например:

```

```

```
    ↓
```

```
Приложение
```

```
    ↓
```

```
Google
```

```
    ↓
```

```
"Разрешить доступ?"
```

```
    ↓
```

```
Приложение получает authorization code
```

```
    ↓
```

```
Получает access token
```

OAuth 2.0 - это **про авторизацию (доступ к ресурсам)**, а не непосредственно про аутентификацию пользователя.

·  **User** - пользователь.

·  **Client** - приложение, например frontend.

·  **Authorization Server** - сервер, который аутентифицирует пользователя и выдает токены. Google, Auth0, Keycloak, Amazon Cognito.

·  **Resource Server** - API, которое принимает Access Token и предоставляет защищенные данные.

Он позволяет приложению узнать, **кто именно пользователь**, используя Identity Provider.

# Access Token vs Refresh Token

||**Access Token**|**Refresh Token**|
|---|---|---|
|Назначение|Доступ к API|Получение нового Access Token|
|Срок жизни|Короткий|Длинный|
|Используется в API|Да|Обычно нет|
|Может быть JWT|Часто|Не обязательно|
|Нужно хранить на сервере|Не обязательно|Часто да|
|При краже|Можно выполнять операции до истечения срока|Может позволить получать новые Access Token|

### Важный момент

**Access Token можно декодировать, если это JWT. Refresh Token нельзя считать «недекодируемым» просто по определению.**

Refresh Token часто делают в виде случайной строки:

```
8f7a9c2e1b4d6...
```

Поэтому там действительно нечего декодировать. Но технически Refresh Token тоже может быть JWT.

Для проверки структуры JWT удобно использовать, например, **jwt.io**, но не стоит вставлять туда реальные production-токены.

# Валидация, идентификация, аутентификация и авторизация

## Валидация

**Валидация** - проверка того, что входные данные соответствуют требованиям системы.

Например:

·        email имеет корректный формат;

·        пароль не пустой и соответствует требованиям;

·        обязательные поля заполнены;

·        число находится в допустимом диапазоне.

Валидация может выполняться **на клиенте и на сервере**. Клиентская валидация нужна прежде всего для удобства пользователя, но сервер **обязательно должен валидировать входные данные самостоятельно**, потому что клиенту доверять нельзя.

Например:

```
Frontend
```

```
   ↓
```

```
email: "test"
```

```
   ↓
```

```
валидация
```

```
   ↓
```

```
"Некорректный email"
```

Но даже если frontend пропустил запрос, сервер должен проверить его еще раз.

Если запрос не соответствует ожидаемому формату или нарушает требования к входным данным, сервер обычно возвращает **400 Bad Request**. Точный статус зависит от API и характера ошибки.

---

## Идентификация

**Идентификация** - определение того, **кого пользователь представляет собой**.

Например, пользователь сообщает:

```
email: user@example.com
```

Система находит пользователя с таким идентификатором:

```
user@example.com → User #123
```

То есть идентификация отвечает на вопрос:

**«Кто ты?»**

Важно: сама по себе идентификация еще **не доказывает**, что пользователь действительно является этим человеком.

Например, злоумышленник тоже может ввести чужой email.

---

## Аутентификация

**Аутентификация** - проверка того, что пользователь действительно является тем, за кого себя выдает.

То есть:

**«Докажи, что ты - это** [**user@example.com**](mailto:user@example.com)**».**

В качестве доказательства могут использоваться разные факторы:

·        **что-то, что пользователь знает** - пароль, PIN;

·        **что-то, чем пользователь владеет** - телефон, аппаратный токен (USB устройство с токеном), passkey;

·        **что-то, чем пользователь является** - биометрия.

Например:

```
Идентификация:
```

```
email → user@example.com
```

```
Аутентификация:
```

```
password → правильный
```

После успешной аутентификации сервер может создать сессию или выдать токены.

## Авторизация

**Авторизация** - проверка того, **имеет ли уже аутентифицированный пользователь право выполнить конкретное действие или получить доступ к конкретному ресурсу**.

То есть:

**«Тебе разрешено это делать?»**

```

```

Проверку авторизации нужно выполнять **на сервере для каждого защищенного действия/ресурса**, а не полагаться на скрытие кнопок на frontend.

### 401 vs 403

**401 Unauthorized**:

Сервер не может считать запрос аутентифицированным - нет действительных учетных данных.

```
Нет сессии
```

```
Нет токена
```

```
Токен истек
```

```
Токен недействителен
```

```
        ↓
```

```
401
```

**403 Forbidden**:

Сервер понял запрос и кто пользователь, но **пользователю запрещено выполнять это действие**.

```
Пользователь аутентифицирован
```

```
        ↓
```

```
Но нет необходимых прав
```

```
        ↓
```

```
403
```

HTTP-стандарт именно так различает эти статусы: `401` связан с отсутствием действительной аутентификации, а `403` - с отказом сервера выполнить запрос, несмотря на то что запрос понятен.
